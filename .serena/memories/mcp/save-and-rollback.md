# MCP save results and rollback notices

- Start at `ExecuteCodeTaskHandler` in the plugin and `Tool`, `PluginBridge` and `RollbackNotices` in the server. For what `penpot.waitForSave` and `contentrollback` observe in the shared frontend queue, see `mem:frontend/plugin-api-to-cljs-binding`.
- `execute_code` waits for layout before the code if the layout API is available, then waits for save. Layout wait errors are logged; save failure, timeout or rollback during the wait fails the call. Keep the save wait outside the catch that only logs layout errors. Missing `waitForSave` is an API compatibility error, not permission to skip the check. Leave room in the tool timeout for both waits and the code itself.
- Check workspace readiness at each wait because the code can navigate. Dashboard calls skip both waits so a prior workspace persistence error does not turn a successful management call into a failure. Without `penpotMgmt`, keep the waits enabled.
- Rollback notices report events carried by a plugin task response, not proof that the current tool caused the reverted edit. `Task.sendResponse` attaches pending events and acknowledges them after handing the response to the UI for forwarding. The server prepends the notice to the tool response, including when the task failed.
- `RollbackLog` writes through to per-file plugin local storage and falls back to memory if storage fails. When a late task response has no waiter, the server returns its events as `unclaimed-rollbacks` for a later response if the socket is still open; otherwise the notices can be lost. The handoff is not an end-to-end acknowledgment.

# MCP plugin connections

- Start at `PluginBridge`, `dispatch/MultiInstanceTaskDispatcher` and `RedisBridge` under `mcp/packages/server/src/`, and `main.ts` and `ReconnectPolicy.ts` under `mcp/packages/plugin/src/`. For OAuth client authentication, see `mem:mcp/oauth`.
- The browser gets `mcp-ws-uri` from frontend config: an explicit override or the instance public URI joined with `mcp/ws`. Keep that same-origin proxy routed to the matching MCP process in each devenv; offset host ports rather than internal ports. Sockets live only in the owning Node process. PostgreSQL holds access tokens and profile settings, not a socket registry; Redis routes cross-instance work. See `mem:devenv/core`.
- `RequestGuard` protects HTTP and WebSocket entry points; keep it ahead of plugin messages. Single-user mode defaults to loopback even in remote mode; multi-user mode relies on user tokens. Check the proxy's forwarded `Host` and the plugin iframe's actual `Origin` against the configured hostnames, not URLs or ports. See `RequestGuard` and the environment table in `mcp/README.md`; bridge test doubles must provide the guard.
- Session IDs are stable per tab and file, so reconnect can reuse an ID while the previous socket is still open. For the same user and session the latest connection wins. Across processes, displace only after seeing a foreign claim published after the local claim, using Redis channel order rather than clocks. Discovery deduplicates by session ID.
- WebSocket close `1008` stops the plugin's automatic reconnect; other close codes use capped backoff. A first connection rejected before `connected` never arms the frontend fallback watcher. Check the reported close reason and use the MCP menu to reconnect after correcting the cause.

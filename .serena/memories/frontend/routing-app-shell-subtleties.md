# Routing and app shell

- Start at `app.main.ui.routes`, `app.main.router` and `app.util.browser-history`. The token is `location.search`, not a store field; preserve the configured `public-uri` origin and subpath. The route table and legacy hash compatibility live in `app.main.ui.routes`.
- Push of the current token does not write or notify; replace always writes and notifies, even for the same token, so URL corrections reach the router. `app.util.dom/replace-history-state!` intentionally rewrites without routing; do not substitute a notifying replace.
- Route data uses query params. A repeated param can decode as a vector; use `rt/get-query-param` for a scalar. Use `rt/token->query-string` at the SSO boundary: the server owns the destination origin. Use `rt/token->url` for a client-side absolute URL; do not require `screen`, since root flows can carry params such as a template without a route name. See `mem:backend/auth-permissions-product-domains`.
- `rt/nav-raw` exits the router; tests observe its destination by dereferencing the event, not by looking for an app listener. Unknown or empty routes verify the profile and teams before redirecting so root and invitation flows do not race. See `mem:frontend/auth-events` for login and invitations.
- Use the team-scoped navigation helpers in `app.main.data.common` rather than building the route at the call site. Their private `resolve-team-id` considers the team already on screen before the profile default, so the user's personal team does not replace the current team. An invalid team route fails explicitly rather than rendering a blank shell.
- For store exceptions, React boundaries and report limits/classification see `mem:frontend/error-reporting`. For the client reaction to lost membership and job events see `mem:frontend/websocket-notifications`.

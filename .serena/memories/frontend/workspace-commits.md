# Workspace commits, rebase and undo

- Start at `app.main.data.changes`, `app.main.data.persistence.commits` and `app.main.data.workspace.undo`. For the shared change vocabulary see `mem:common/changes-architecture`; for save ordering see `mem:frontend/workspace-state-persistence-subtleties`.
- `commit-changes` requires edit permission, no historical preview and no save-failure lock. Its refusal completes an empty stream, not nil. `:ignore-save-lock` is for rollback compensation and information derived from existing commits (position data, component touch), not user edits or an origin allowlist. Remote changes apply through `commit`, outside this local gate.
- When a peer commit arrives, undo pending edits for that file, apply the remote change and replay local redo. Read pending edits from both the save queue **and** the unflushed buffer; otherwise the local and server order can disagree. Isolate files and versions, and keep index updates for all replay legs.
- An undo group is one user action even if it spans several files; dependent commits such as component sync must inherit it. Persistence uses this same group for rollback. A stacked commit that records undo may inherit the current history entry's group; a repair that records no undo must not inherit it or failure could roll back the previous user action. Let an open nonempty transaction keep its grouping.
- Do not move the undo index when an active editor interaction or save lock blocks the corresponding commit; grid editing has its own allowed path. Preserve the pure-translation flag when replaying an undo entry or building one in a test harness. Combining entries keeps that flag only when every entry is a translation, so replay skips the same component and thumbnail work as the original.
- Local commits feed independent undo, persistence and render consumers. The WASM-derived text-position commit excludes its own tag from the watcher to avoid a loop.

# Workspace persistence

- Start at `app.main.data.persistence`, its `commits` and `lock` namespaces, and the `bundle-fetched` flow in `app.main.data.workspace`. For ordinary state and refs see `mem:frontend/workspace-store`; for creating, replaying and undoing edits see `mem:frontend/workspace-commits`.

## Ordering and partial saves

- A flush moves only its own commits out of the buffer; edits arriving mid-flush remain. Batch by file and version and keep per-commit metadata through `update-file-v2`; flattening the changes would remove the server's partial-rejection boundary. See `mem:backend/file-data/save` for the server contract.
- Editor saves POST to `/api/main/methods/update-file-v2`, with `id` in the query string and the Transit body. The body carries `:id`, `:session-id`, `:revn`, `:vern`, `:features`, `:repair-in-response true` and a non-empty `:commits` vector in edit order; each commit sends only `:commit-id` and `:changes` (the local redo vector). Local redo and undo stay on the queue; the server receives no undo and stores no inverse. Retries keep IDs and changes. There is no fallback to `update-file`: a missing v2 endpoint or an older schema that rejects the opt-in halts the queue. Verify both request and response at every save target before serving the editor; accepting `:changes` alone does not prove confirmation support. `save-request-timeout-ms` (7 min) wraps this request and fails it as a transient `:network` error.
- A `:rejected` response can already have saved part of the batch. Roll back rejected groups before acknowledging the saved entry. Within each affected file revert from the first rejected or grouped commit onward, following any newly affected groups across files; unrelated groups in other files stay. If a reverted group was already partly saved, enqueue compensation, including for unloaded files. Undo pending edits before re-applying intervening peer changes and keeping valid local redo; absolute undo values applied in isolation can overwrite later peer edits.
- Rebase is not a normal commit, so dependent consumers cannot rely on commit watchers. Notify rollback only once the rebased or reloaded data is in state; comments persist through their own RPC, library sync needs a landed save before marking success, and thumbnails must not upload stale pre-rollback output. Invalidate stale path or text editor drafts before they can commit again on exit. Follow `apply-rollback-plan` and `notify-rolled-back` for these entry points.
- v2 answers pre-save `:revn`/`:vern`, the attempt's ordered `:written` rows and `:saved-revn` only after a write; there is no `:lagged`. `:repair {:id :revn :changes}` is inline only for edit→repair. Validate the acknowledgement and rejected suffix against the captured POST before changing the queue. Settle from the captured base, the exact applied predecessor IDs in `:recovery`, and the repair ID for repair→edit; revision maxima, timestamps and a commit event alone are not proof. `:recovery` reports the mode for missing rows, not a reason to read a fully proven interval; an ordinary edit that differs from the POST needs a full read even without a gap. Apply the HTTP repair after the accepted edit and before queued or buffered edits of that file and `vern`; it never enters the save queue or undo history. The confirmed head stays queued but is excluded from rebase; track bounded applied row IDs from the full file topic and require the proven predecessor for repairs.
- A recovery GET installs only for the same opening and `vern`, at or above the save confirmation and revisions seen meanwhile, and replays unconfirmed edits while preserving unrelated undo and library state. A failed, superseded or new-`vern` read keeps pending edits and settles the confirmed head without resending; a timeout can still leave a write from the first POST with no deduplication, so classify before rejection rollback and reconcile even after a partial or total rejection.
- `rp/cmd!` reads `::rp/cache` from params metadata, never from the RPC payload; use `"no-store"` when a file read must bypass the browser HTTP cache and its conditional 304 revalidation. Save recovery uses it even with catch-up off.
- A post-save library read owns the confirmed head by `:entry-id` and the POST's original `vern`, not by a removed `::save-result`; bind each read and Retry to an attempt token and opening. Track the library's visible `vern` per GET: if it changes before the GET finishes, discard the outcome and restart once with a fresh token and `no-store`, keeping the accumulated minimum revision. A valid linked-library GET must cover that minimum and cannot return to the POST's original `vern`; preserve link metadata and replay only unconfirmed edits of the installed `vern`. If the library is no longer linked, finish on result or Retry without installing and still emit `commit-persisted`.
- The open file consumes only its full file topic; the team topic applies deltas to linked libraries. Use the event's `:library-change true` marker, never cached `:is-shared`, for applied-delta effects and carry it through a needed read. Give the repair toast priority over the token info toast; a fallback answer with `:media-relinked` confirms the save but requires a read of the final image refs.
- `:file-catch-up` is off by default. An eligible base starts from a `get-file` fetched with `no-store`; a new GET replaces the in-memory proof even at the same `revn`/`vern`. WebSocket or POST progress does not extend that proof unless the incremental reader verifies the row IDs and replay eligibility. One catch-up request per opening coalesces gaps, reconnects and saves waiting on predecessors; `until` excludes the editor's own edit and the GET confirms that adjacent row by ID without returning it. Exact WebSocket proof cancels the tied GET; an unsafe or failed read hands control to full reconciliation.
- Reconnection asks for the file-subscription ready message before reading incrementally. A `vern` change from full reconciliation switches the live file, discards old-version pending commits and shows the restore modal once; count only unconfirmed commits as unsaved. During replacement, a newer WebSocket revision for another `vern` raises the full read's minimum without applying its delta.
- A file restore changes `vern`: do not replay queued, buffered or saved edits from another version. A stale send or late failure must not halt the new version. Pending replay on reopening goes queue then buffer; if replay throws, retain the queue and show loaded server data.

## Failures and recovery

- `app.main.repo/retryable-types` is shared with error reporting and persistence. Repo retries only GETs; saves own their retry budget, including save-only server-busy cases. Keep the stalled-save report deadline shorter than the request timeout. A slowly failing request may still be applying server-side, so cap repeated slow attempts separately from fast network failures.
- A live retry episode owns the runner and its budget. New edits queue behind it; they do not start another runner. Timer and online resumption apply only to the live episode; leaving the workspace suspends retries and reopening can restore them. A retry reuses its `:commit-id`, but never sends a second request while the first remains in flight. Stub timers for tests rather than rebinding across `await`.
- Keep permanent failures halted and their edits queued so `wait-persisted-or-error` keeps rejecting; snapshot creation must not treat an unsaved edit as saved. Initialization does not lift a halt. Reopening or changing roles invokes recovery: retry a transport failure still covered by the slow cycle; otherwise release the failed file before other files can drain. A role change that leaves a viewer does not release permission-denied edits. On release while the file is still open, also revert affected edits on canvas.
- A terminal `:params-validation` (malformed change records) writes nothing and is not retried; an HTTP 200 with `:rejected` is not a terminal failure. `debug.failNextRollback` arms a one-shot local failure for pending commit IDs in the open file: it leaves the buffer, queue, HTTP request and compensation data untouched and exercises the file reload path.
- A repair or fresh server base makes affected undo uncertain through queueing and `:saved`. Exclude unsafe persisted compensations, count them as `:kept-saved` and ask the user to reconcile instead of applying old inverses. Keep their identity through buffering and queueing so one can be dropped before its first POST; a POST already attempted cannot be canceled. Announce `:rolled-back` for a file needing a read only after the read installs.
- A backoff timer's token stays live while the head waits for its recovery read: retry the same head with the same budget and do not spend an attempt on a failed read. `discard-commit` clears the head's episode and token atomically so a read of the next file cannot wake the queue with a stale retry. A 504 `:statement-timeout` or admission 429 marks the save uncertain despite the busy classification, since audit runs after commit.
- Only users who can edit get the save-failure lock. Cancel gestures before interrupting, so stale previews do not commit; restore the prior read-only choice without overwriting the separate WebGL context-loss state. The Inspect tab's read-only state is not itself the save lock. See `mem:frontend/error-reporting` for how failures are reported.

## Leaving and exporting

- Queued **or** buffered edits hold the unload guard and prevent a successful save wait from settling. The `:saved` status alone does not prove the buffer is empty. Flush on visibility-hidden or blur; pagehide/beforeunload are too late for an async request. Mock leave signals before initializing persistence in tests.
- Export, `.penpot` download and dashboard duplicate wait only for the requested files before starting. Timeout or a save error ends that wait, not the action. A local export can include unsaved edits; a server export or duplicate can miss them. The duplicate flow owns its one completion toast so a generic success notice cannot overwrite the warning.
- Follow `persistence-failed` for `save-failed` audit: report when the user is notified, even if the presentation delegates to authentication handling. A pre-repair snapshot is discoverable in version history through the repair notice; keep that link useful when changing history presentation.

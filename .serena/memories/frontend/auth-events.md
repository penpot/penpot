# Auth events and invitations

- Start at `app.main.data.auth` and `frontend-tests.data.auth-test`. `logged-in` emits the `signin` identify event using `profile-origin`: `::ev/source` and `::ev/activation` come from profile metadata; `:auth-backend` and invitation presence come from the profile. Do not remove the metadata as unused.
- `schema:auth-origin` defines the vocabulary. Login omits activation; registration uses `immediate` or `email-verification`. LDAP is always `login`, even when the directory provisions the account on first login. `login-from-token` maps `:auth` to login and `:verify-email` to registration with email verification; an unknown issuer produces no source.
- `auth-origin` removes nil fields and validates with `assert`, which release builds elide. Invalid origin data can therefore reach production events; keep emitters and tests aligned with the schema. `signin` always supplies a boolean `from-invitation`.
- An invitation navigates to token verification independently of `teams-fetched`: waiting for teams can strand the invitation when `fetch-teams` fails. The normal team redirect emits nothing for invited profiles, so it cannot move them away from verification. `login-from-register` carries the invitation into `logged-in`; `register-profile` returns it, while `verify-token` emits the acceptance.
- OIDC carries the invitation in the `:auth` token and follows `login-from-token` to `logged-in`; this can visit token verification twice. The active-profile branches in `ui/auth/login_modal.cljs` and `ui/static.cljs` still bypass `logged-in`; do not assume all registration paths emit `signin`. See `mem:backend/auth-sso`.
- Backend `register-profile` success events carry `activation` without a constant `action`; retry events use `action` in context to distinguish outcomes. Telemetry filtering keeps `source` and `activation`, not `action`; see `mem:audit-log`.

# Production infrastructure (services Penpot depends on)

Backend (`app.config`, `PENPOT_*` env vars) is parameterized; deployments choose providers.

## Services

- **PostgreSQL**: durable store: profiles, teams, files, sessions, audit, the jobs work queue, the cron registry and migrations. File data also lives here depending on the file-data backend. One shared DB across all backends.
- **Redis (Valkey-compatible)**: per-backend message bus and cache: collaborative-editing broadcasts and team/profile notifications, the file-summary cache, rate-limit counters and the dispatcher→runner hand-off. `PENPOT_REDIS_URI`. A burst of client-side `RedisCommandTimeoutException` with the exporter healthy is the JVM paused or starved, not Redis: the timeout fires because nothing reads the reply.
- **Object storage**: backends `:s3` and `:fs`. S3 in prod; devenv uses RustFS. Holds uploaded media, file-data when the file-data backend is `storage`, exports. Backend-side details (resolve, dedup, bucket set, object lifecycle, and file-data backends): `mem:backend/storage`.
- **SMTP mailer**: invitations, password resets, email verification (sent via the `:sendmail` worker job).
- **LDAP** (optional auth provider): helpers in `app.auth.*`, gated by `enable-login-with-ldap`.

## Task queue and worker model

Async jobs are enqueued via `jobs/submit` (`app.jobs`), which inserts a row into the shared Postgres `job` table tagged with its tenant and queue. Submission is **fire-and-forget**: RPC handlers never poll and never wait. The completion signal is the job row's status, which the creation commands read back to answer with the state of the job they just created. A job submitted with an owner profile publishes its progress on that profile's msgbus topic after each transaction commits; the binfile commands are the callers that pass the owner. Soft-delete RPCs return immediately after marking the top-level row, leaving the cascade and reaping to workers.

Workers run on backends with `enable-backend-worker` in `PENPOT_FLAGS`. Each worker-enabled backend has a dispatcher that claims jobs and hands them to **its own** Redis list, and one or more runners per queue that execute them and update the Postgres row. The hand-off is purely intra-backend; cross-backend coordination happens at the Postgres row level. The queues are `default`, `webhooks`, `cron` and `binfile`: `binfile` carries the heavy work of a user job, so a long export or import does not block the default runner that serves the delete cascades.

## Cross-backend safety

Postgres row locking is the only correctness primitive: job claims, cron firing and the job-handler-internal locks (for example, the file-gc scheduler locks its candidate rows) all rely on it. This makes the work-claim path safe across any number of worker-enabled backends.

Two known race patterns survive multi-backend operation:

- **Cron dedup is best-effort.** The lock on `scheduled_task` is released when the task body finishes. If two backends' cron timers fire for the same scheduled instant with a gap larger than the task body's runtime, both execute it. Penpot's cron entries are idempotent; the exception is `:telemetry`, which would double-report. The audit consumers are not served by cron any more: each one is a loop in a thread and takes a session advisory lock for the whole pass, so a double-fire of a cron entry cannot overlap them.
- **`jobs/submit ::dedupe` / `::debounce`** are not affected by it: the row is inserted as deduped and a partial unique index (`status = 'new'`) admits a single not-started row per tenant/name/queue/label. The insert resolves the conflict with `ON CONFLICT DO NOTHING` (skip) or `DO UPDATE` (refresh the schedule and the params of the pending row), so there is no delete before the insert and no cross-backend duplicate. Neither gives "at most one execution": a row that already left `new` (dispatched, running, retrying) does not block the next submit.
- **`jobs/submit ::skip-if-active true`** works the same way one level up: the row is inserted as exclusive and a partial unique index admits a single live row (`new`/`scheduled`/`running`/`retry`) per tenant/name/queue/label, resolved with `ON CONFLICT DO NOTHING`. What it does not give is "at most one execution": the row can go terminal while its work is still running (a retry, an `aborted` orphan), so the work itself must be claimed on the data it touches.

Penpot in production lives with both: horizontal-scale deployments accept "exactly-once" as "essentially-once for idempotent operations." Devenv parallel instances handle it by running workers only on ws0 (see `mem:devenv/core`).

## Jobs observability

Worker-enabled, writable backends publish unified jobs metrics through the normal Prometheus registry. One submit counter splits by `outcome` (`created`, `skipped`, `refreshed`), and the dispatch and retry counters are keyed by job name; terminal outcomes are the `_count` of the total-time histogram (`completed`, `failed`, `cancelled`, `aborted`), which counts the system-side aborts (an expired orphan lease or a job never claimed after being scheduled), so there is no separate terminal or orphan counter. Histograms separate claim wait (how late the claim happened), handler execution and total job age, plus dispatcher batch timing and size. `queue` survives only on the batch size: a batch mixes job names, and every other measurement is keyed by a name that already determines its queue. SQL-backed events are recorded after the outer PostgreSQL transaction commits. There is no gauge and no sampler: the backlog and the age of the oldest pending job are one SQL query when an operator asks. All labels are bounded operational values; job IDs, profile IDs, params and error text are excluded. Read-only backends do not start the workers.

## Draining one instance

Each backend has a per-process availability flag (`app.health`, a global atom). While offline, `/readyz` answers `503 OFFLINE` without querying the database, so the load balancer removes that instance from rotation while requests in flight still finish. Operator surface: `app.srepl.main/set-offline` / `set-online`; a restart comes back online. Nothing stays stuck after an instance leaves: a job handed to a queue (`scheduled`) that no worker claims within the lost window is aborted with `:lost`, and a `running` job whose lease expires is aborted with `:orphan`. The in-flight work is abandoned, not resumed, and the sweep never retries it.

## Touching production data

Production runs the deployed toolbox, not the devenv one:

- **No psql meta-commands there.** `scripts/psql` and `\set`, `\if`, `\copy` do not exist in production, so a data script must be **plain SQL**, copy-pasteable into any client.
- **Start from the ids, not from an inventory.** The ids come from the error or the logs. Unbounded queries over tables with tens of millions of rows (`storage_object`, `file_media_object`) do not finish in a reasonable time; bounded to an id list they are index lookups.
- **One query per reference column.** Two columns in one `IN (col_a, col_b)` lose the index and scan the whole table; split them.
- The read-only replica cuts long queries: see `mem:prod-infra/grafana`.
- A migration that builds an index runs inside the migration transaction, so it cannot use `CONCURRENTLY`, and a plain `CREATE INDEX` locks the table against writes for the whole build. On a large table (file saves write to `file_change` on every save) build the index out of band, before deploying, with `CREATE INDEX CONCURRENTLY` on its own (never inside a transaction block); the shipped migration uses `IF NOT EXISTS`, finds it and skips the build (it still takes the `ALTER`s' locks, so the operator registers the step in `migrations`; the consumer-generalization runbook registers it first of all, before the DDL). A concurrent build interrupted midway leaves the index invalid: drop it and retry (check `pg_indexes` and `pg_index.indisvalid`). The runner applies **every pending step in one transaction**, so pre-applying one migration of a group does not avoid the locks of the others: that is why the consumer generalization ships as `0159-consumer-generalization` (plus `0154-add-job-table`, which a 2.19 database does not have) whose runbook lives in `operations/2.20.0-consumer-generalization.md` (the migration comment points to it) — the `IF NOT EXISTS` ALTERs (metadata-only), the `CONCURRENTLY` unique indexes (`job__live_exclusive__uniq`, `job__new_dedupe__uniq`, `audit_log__xid__seq__idx`), the `seq` backfill (a single ordered `UPDATE`, no table lock, re-runnable) with the sequence reserved above it (`setval(count + 1000000)`, so new rows sort above the history), the `CHECK NOT VALID` + `VALIDATE` + `SET NOT NULL` for `audit_log.seq`, and the `indisvalid` gate before deploying. It opens by registering the steps (`INSERT INTO migrations`, `module = 'main'`, `step = '0154-add-job-table'` and `'0159-consumer-generalization'`) so the runner skips the group from the first minute, whatever deploy lands in between, and the steps below become the only path that applies the schema; without that row the guards skip the work, not the `ACCESS EXCLUSIVE` locks nor the backfill scan. Before that, the runbook stops the legacy archiver **and its GC** with the flags `:audit-log-archive` off and `:audit-log-gc` off (the web instances keep writing; the two versions do not serialize each other, so a concurrent old archiver/GC could archive and delete rows the new consumers have not read yet) and deletes the already-archived rows, so the first deploy replays only the unarchived backlog. The legacy mark and its indexes stay; a later release drops them with catalog operations. The new GC is gated by `:audit-log-gc` (the old 2.18 flag): keep it off while the old and new versions coexist and turn it on after the rollout; with no consumer enabled it deletes nothing. `IF NOT EXISTS` matches by name, so an `INVALID` index from an interrupted build satisfies the migration too and the dedupe/exclusivity stops enforcing silently: the gate is mandatory. The pending queue never shipped: the migration does not create `audit_log_pending` and only drops its foreign key if a pre-release database has the table, so leftover rows there cannot block the new GC; the runbook documents the optional `DROP TABLE` for such a database.

# RPC concurrency limits

- Start at `app.rpc.climit/wrap` and `backend/resources/climit.edn`. A plain `::climit/id` keyword shares one limiter across calls in the process; `[id key-fn]` declares one keyed limit; `[[id key-fn] ...]` declares several. A keyword in the key position looks up a param. `::climit/key-fn` metadata is not read, so putting it beside a bare ID silently makes the limiter shared.
- Acquire command limits before root limits, and the per-profile limit before its global counterpart. Otherwise callers waiting on heavy work can hold root permits and block unrelated RPCs, or commands acquiring shared limits in opposite orders can deadlock. Declare limits at the RPC boundary, not inside handlers; use shared helpers rather than invoking another wrapped RPC.
- Give every declared ID a config entry with a bounded queue and permit wait timeout. Keep the deployed config aligned with shipped declarations: a missing entry skips that limit, and root limits do not bound waiters held outside them. A permit timeout bounds acquisition, not the running handler: a stalled remote image body read can still hold both image permits. See `rpc_climit_test.clj` for declaration order and config coverage and `climit_test.clj` for wait bounds.
- `penpot_rpc_climit_waiting` is a gauge of callers waiting for a permit, summed over keys for each limiter name and instance. Do not replace it with the last active key's queue size. Pair each increment with one decrement on acquisition or failure; concurrent publications can arrive out of order, so the component sampler republishes the current total.
- Count rejections with `penpot_rpc_climit_rejected_total` (`queue-full` vs `timeout`), not log lines: an isolated timeout can log at `TRACE`. Use `app.rpc.climit` logs to identify a key, not metric labels. When waiting stays high and `penpot_rpc_climit_timing_count` stops increasing on one instance, check thread dumps for parked permit waiters before blaming CPU saturation.

# Backend SSO and registration

- Start at `app.auth.oidc`, `app.rpc.commands.auth` and `app.rpc.commands.ldap`. For HTTP session and token boundaries see `mem:backend/http-rpc` and `mem:backend/auth-tokens`.
- LDAP binds the session to the directory-returned email, not the typed login: aliases and multi-valued attributes can resolve to a different profile. Redis-backed account lockout checks use the typed identity, but successful login clears the counter for the profile actually logged in. Lockout and RPC rate limits use the `app.http.errors` 429 path; keep `retry-after` and rate-limit headers available through CORS.
- `check-nitrate-sso` receives the client route as a query string, not an absolute URL. `build-dest-url` validates parameter keys and builds the destination under `public-uri`; invalid input falls back there. Accept root routes without `screen`, and keep callback revalidation for older state tokens. The state token binds the SSO grant to the profile that initiated it: a different session must not receive that grant.
- Generic OIDC authorization stores a trusted alternate origin (request `:app.http/trusted-origin`, see `mem:backend/http-rpc`) as `:origin` in signed state; the callback re-applies it to the configured public URI so the token-exchange `redirect_uri` and redirect targets stay on the alternate domain. Organization SSO mirrors it through `build-organization-sso-auth-redirect-uri :origin`. MCP OAuth sits outside the root middleware chain: it wraps its own routes with `wrap-trusted-origin`, stages the origin in its Redis `:request` record at authorize time, and re-applies it in `decision` for the approval redirect, metadata and code-exchange `iss`.
- A client-supplied organization ID requires `app.nitrate/organization-access?` before SSO; callers without organization access get the no-access short circuit, not an SSO challenge.
- When public registration is disabled, a matching invitation can allow registration. Password registration rechecks the non-expired invitation row under lock. OIDC registration requires `:registration`, `:oidc-registration` or an invitation whose member email matches the provider email after `clean-email`; the callback verifies it and registration revalidates it under lock when the flags are off. Only recognized OIDC provider types take the SSO registration path. Keep invitation identity checks on authenticated login too.
- Test both the root and workspace route forms, malformed redirect targets, changed sessions and invitation email mismatches. Frontend query-string construction: `mem:frontend/routing`. For test flags and setup see `mem:backend/testing`.

# Backend WebSocket subscriptions

- Start at `app.http.websocket` for connection ownership and revalidation, and `app.rpc.notifications` for internal announcements. The connection registry and profile index share one atom, local to the backend instance; each connection's `::ws/state` separately owns its subscriptions. Use the correct namespaces for profile/session fields versus `app.util.websocket` fields: a missing session ID can silently drop every output message.
- Notification WebSockets negotiate transit by default or JSON via `Accept`/`_fmt=json`. Validate client messages after decoding and before the receive hook or dispatch; lifecycle events are server-only. JSON converts known IDs, including pointer `page-id`, to UUIDs; transit clients send native types. Invalid decodable messages receive a bounded, non-sensitive validation error while the connection remains open. Permission checks and subscription revocation remain separate from schema validation.
- Access is checked when subscribing and rechecked afterward. Mutations announce permission changes on the internal bus after commit, so a watcher on another connection sees committed state. A team-level event resolves members in the watcher instead of publishing one event per member. Keep notification helpers outside `app.http.websocket` to avoid the command dependency cycle.
- An announcement triggers a fresh decision; it does not prove access was lost. Check resource existence as well as read permissions, including the organization-owner fallback. A deleted file, project or team must not remain readable through that fallback, while a downgrade to viewer or a live non-member organization owner can remain readable. Team rechecks add an existence gate even though the original team subscription does not. See `mem:backend/permissions`.
- The relay also rechecks on an interval, covering external ownership changes, direct SQL and missed announcements. Reuse one tick through message turns and prioritize it over the subscription channel so busy traffic cannot starve revalidation. Closing the channel ends the relay. Both interval checks and the announcement watcher deliberately fail open on lookup errors; interval checks rethrow interruption. Size the cost before shortening the interval.
- Use the dedicated internal revocation topic, never `uuid/zero`: the system topic is piped directly to clients. The bus reaches other backend instances; directly closing locally registered sockets does not. Close functions are idempotent and remove the subscription before later messages can reuse its topic. See `mem:prod-infra/core` and `mem:frontend/websocket-notifications`.

## Tests

- `backend-tests.http-websocket-test` exercises the real registry and Redis-backed bus. Watcher tests must register the connection and clean the registry between tests. To test the periodic path, remove access without a command that announces it; otherwise the watcher can hide a broken interval. To test the watcher itself, change access without announcement and publish one synthetic event. Exercise deleted resources and the organization-owner fallback as well as access that remains valid.
- Compile the watcher params schema explicitly because the normal test system does not start the watcher. For registry references and assertions at system startup see `mem:backend/integrant-schemas`.

# File-data storage and persistence boundaries

- Start at `app.features.fdata` for payloads, `app.binfile.common` for the file-map boundary, and `app.tasks.offload-file-data` for moving data to object storage. For fragment and version lifetimes see `mem:backend/file-data/reads-and-versions`.
- `file_data.storage_object_id` is the authoritative reference; metadata is not a fallback. `legacy-db` reads old payloads only; startup normalizes that configured write backend to `db`. If an old binary still reads or writes a metadata pointer, it cannot safely coexist with writes that remove it. See `mem:prod-infra/core` for the general deployment constraint.
- Carry the old pointer from the persisted row through updates under the file-row lock. `fdata/upsert!` touches it so the GC can reclaim the replaced blob, and rejects a stale expected pointer rather than leaking the object it would overwrite. `binfile.common/update-file!` preserves the old pointer from its read map and returns the pointer actually persisted; inserts must not inherit the source pointer. Strip both the column and any residual metadata pointer from file responses: direct object authentication does not verify file permissions.
- Offload and the other writers serialize on the file row. Offload moves live DB rows in one transaction per file; later writes still use the configured default backend, not the offloaded row's backend. If a write aborts after the upload is valid, touched GC checks the blob's references; unfinished uploads use pending GC. Batch deletion must touch the old object and restore must clear the deletion mark on live references. See `mem:backend/storage`.
- The foreign key must be `DEFERRABLE INITIALLY IMMEDIATE`: a referenced blob must not be removed, and a violation must reach the GC's chunk error handler rather than appear at commit outside it. The reference scan uses the indexed column, not metadata. See `mem:prod-infra/core`.
- `file_change` and `file_data` have matching partition bounds; include `file_id` in lookups and group bulk purges by it so PostgreSQL can prune partitions. Advance `file_change.updated_at` on application writes: it is the watermark for delta copies. The legacy copy is not cleaned up automatically.
- `file_change_refs` is derived state, hash-partitioned like `file_change` and keyed by its complete `(file_id, id)` identity. Its `ON DELETE CASCADE` prevents orphan index rows. `fragment_ids = '{}'` is coverage with no refs (all current revisions); an absent row is unknown.
- Reference indexing uses `kind`, not `label`, to distinguish snapshots from revisions. A missing or unsupported kind raises `:invalid-file-change-kind` and cannot create a coverage row. Existing snapshot queries still use `label IS NOT NULL`; the column stays nullable for rollback to the previous version, which inserts without it. No constraint ties `kind` to `label`.
- `index-file-change-refs-scheduler` is triggered per file by audit or by fragment GC, not by cron. It scans uncovered IDs in UUID-ordered pages of 32 and returns `{:file-id <uuid> :scheduled <count>}`, counting only new job rows. `::jobs/dedupe` lets a new signal queue a successor even if the running scan already passed a newly committed ID. Each uncovered change, including revisions, gets an `index-file-change-refs` job, exclusive while live via `::jobs/skip-if-active` and the `(file-id, change-id)` label.
- `index-file-change-refs` indexes one change in its own transaction without loading referenced fragments and returns `{:file-id <uuid> :change-id <uuid> :indexed <boolean>}`. `:indexed` is true only when `INSERT ... RETURNING` confirms a new coverage row, including empty coverage. Errors retry only that change; interrupts propagate unchanged. Publication is idempotent even if a scan enqueued a job for a change that became covered meanwhile.
- Objects GC may purge a snapshot payload before its `file_change` row. If resolution returns no payload, indexing skips the snapshot without recording coverage or requesting a retry; its metadata still blocks fragment marking until covered or purged. Use `fdata/has-payload?` after resolving and before decoding: a present payload that decodes to nil is invalid, and storage read errors still propagate without rechecking the metadata.

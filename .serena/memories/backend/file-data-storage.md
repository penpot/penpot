# File-data storage and persistence boundaries

- Start at `app.features.fdata` for payloads, `app.binfile.common` for the file-map boundary, and `app.tasks.offload-file-data` for moving data to object storage. For fragment lifetimes, save application and snapshots, see `mem:backend/subtleties`.
- `file_data.storage_object_id` is the authoritative reference; metadata is not a fallback. `legacy-db` reads old payloads only; startup normalizes that configured write backend to `db`. If an old binary still reads or writes a metadata pointer, it cannot safely coexist with writes that remove it. See `mem:prod-infra/core` for the general deployment constraint.
- Carry the old pointer from the persisted row through updates under the file-row lock. `fdata/upsert!` touches it so the GC can reclaim the replaced blob, and rejects a stale expected pointer rather than leaking the object it would overwrite. `binfile.common/update-file!` preserves the old pointer from its read map and returns the pointer actually persisted; inserts must not inherit the source pointer. Strip both the column and any residual metadata pointer from file responses: direct object authentication does not verify file permissions.
- Offload and the other writers serialize on the file row. Offload moves live DB rows in one transaction per file; later writes still use the configured default backend, not the offloaded row's backend. If a write aborts after the upload is valid, touched GC checks the blob's references; unfinished uploads use pending GC. Batch deletion must touch the old object and restore must clear the deletion mark on live references. See `mem:backend/storage`.
- The foreign key must be `DEFERRABLE INITIALLY IMMEDIATE`: a referenced blob must not be removed, and a violation must reach the GC's chunk error handler rather than appear at commit outside it. The reference scan uses the indexed column, not metadata. See `mem:prod-infra/core`.
- `file_change` and `file_data` have matching partition bounds; include `file_id` in lookups and group bulk purges by it so PostgreSQL can prune partitions. Advance `file_change.updated_at` on application writes: it is the watermark for delta copies. The legacy copy is not cleaned up automatically.
- Snapshot metadata and revision deltas live in `file_change`; current snapshot payloads live in `file_data`. Queries still distinguish snapshots by label, not by the legacy `data` column or the reserved `kind` column. See `mem:backend/subtleties` for snapshot queries and restore behavior.

# Backend product permissions

- Start at `app.rpc.permissions` and the owning file, team, project and comment commands. Permission failures normally answer `:not-found` to avoid exposing resource existence. Invitation management deliberately answers `:validation` / `:insufficient-permissions` instead.
- File and project roles require live team membership; leaving or removing a member clears team-scoped roles. The organization-owner fallback grants read-only access without membership only for live resources. Soft-delete filtering in `db/get*` requires `deleted_at` in the selected columns. WebSocket rechecks depend on the same rules; see `mem:backend/websocket-subscriptions`.
- Share-link authorization is page-scoped for comments, viewer bundles and file fragments. A view-only bundle includes only live components transitively referenced by the permitted output, including linked-library dependencies; do not derive those dependencies from excluded pages or deleted components. Root-level fragments are not authorized by a share link. Membership bundles have different scope.
- Invitation management is team-admin only; owner-role invitation tokens require the team owner. With `:admin-console`, `check-send-invitations-policy` gates changes and token issuance through a strict Nitrate lookup, but listing remains team-admin only. The policy lookup runs outside the DB transaction. For registration with an invitation see `mem:backend/auth-sso`.
- Comment checks include login state and file/team policy. Preserve share-link page checks before mutation and avoid bypassing existing permission helpers, including their not-found behavior. For webhook and audit emission see `mem:audit-log`.

# Database transactions and advisory locks

- Start at `app.db/transact!`, `tx-run!` and `own-transaction`. `tx-run!` prefers the connection in the cfg over its pool. Passing the very same connection joins the existing transaction, not a savepoint; use an explicit savepoint for partial rollback. Passing a pool instead starts an independent transaction even inside an existing one. `db/run!` obtains or reuses a connection without starting a transaction.
- `db/set-tx-isolation` takes the active transaction's cfg and `:read-committed` or `:repeatable-read`. Call it before the first query of a transaction you own; a joined call would change the caller's transaction. It does not change the connection's default isolation.
- Use `db/own-transaction` only when the write must survive rollback of the caller, as with independent job lifecycle transitions. It drops `::db/conn` to force the next `tx-run!` through the pool and `::db/read-only` so a read-only scan does not make the write read-only too. It does not clear an explicit `::db/rollback`.
- `db/after-commit` runs immediately outside the transaction context managed by `app.db`. Inside it, the callback belongs to the transaction that owns the connection, not the outermost call on the stack. Register it inside the transaction that performs the write. A rollback or rollback-only transaction discards its callbacks; an independent transaction drains its own callbacks at commit.
- Transaction advisory locks end with the transaction. Session advisory locks survive both commit and return to the connection pool; release them before returning the connection. The one-key and two-key PostgreSQL lock spaces are disjoint: file updates and setup use the former, audit consumers the latter. See `app.db/session-try-lock` and `mem:backend/audit-consumers`.

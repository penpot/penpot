# File save acceptance

- Start at `app.rpc.commands.files-update`; for client handling and retry see `mem:frontend/workspace-persistence`, and for version and fragment lifetime see `mem:backend/file-data/reads-and-versions`.
- Partial acceptance requires named commits: `update-file-v2` sends `:commits` with a `:commit-id` on every entry (schema enforced), and the deprecated `update-file` uses `:changes-with-metadata` groups that all carry one. Flat changes or groups without IDs remain all-or-nothing. Try the entire batch first: a later commit may repair an earlier one. On a change failure, `apply-commits` searches for an accepted prefix and returns HTTP 200 with a `:rejected` suffix. `:preexisting-damage` means the data touched by the first rejected commit already failed validation on the base before that commit.
- Persist and broadcast only the accepted prefix. A fully rejected save does not write a revision, change `revn`, or broadcast file changes. Database, I/O, interruption and missing-fragment errors fail the request rather than reject a commit. `app.http.errors` distinguishes transient failures the client can retry from permanent errors; do not classify every I/O error as transient.
- Each `apply-prefix` attempt starts from the original file, resets pointer tracking to its baseline and clears media-reference state. Keep only the accepted attempt's tracked pointers and references. A pointer already marked modified can retain its ID across edits, so leaking failed tracking can persist the rejected version under an accepted ID.
- Prefer the `fdata/with-*` wrappers for pointer loading and tracking. The save path toggles tracking within the same atom for validation and repair; do not replace that with a fresh tracking scope. Under schema validation, decode affected objects on the shared base before attempts so derived maps inherit the cache. Validation timings describe the first attempt; the bisection has its own retry timing. For controlled save failures, see `:debug-save-faults` in `app.rpc.commands.files-update`.
- A written revision stores its payload in `file_data` (`type = 'revision'`) with the same id and deletion date as its `file_change` row: redo in edit order, then the accepted commits' client-supplied undo, newest commit first and in each commit's original order. The count of rejected commit IDs gives the rejected suffix length, not a change count. The server validates the undo schema but neither applies it nor computes an inverse: concurrent edits make that unsafe, and a retry after a lost response can write another revision. The deprecated `update-file` and automatic repair revisions store `:undo-changes []`.
- Each save writes a new payload row, so `fdata/upsert!` passes `:storage-object-id nil`. `file_change.changes` still carries the accepted redo for readers deployed before the payload existed; a later step reads the payload with a fallback to the column and stops writing it.
- The editor opts in with `:repair-in-response true`. A write answers `:saved-revn`; an edit→repair save also answers `:repair {:id :revn :changes}`. `:revn` stays the pre-save revision and `:lagged` keeps timestamp order, so neither timestamps nor the last lagged row identify the saved revision. Edit-before-repair is allowed only after proving the legacy repair-before-edit control: initial errors must match entities and occurrences, or the edit must leave data unchanged. Ambiguous details, pending migrations and media refs that may be relinked keep the legacy order. A relinking fallback answers `:media-relinked true` with `:saved-revn` and no `:repair`; the edit redo carries the final image refs, its undo does not change.
- A repair save writes two revision rows and payloads with the same deletion schedule. The edit keeps its undo and is the row linked from audit; the system repair row has no undo. `revn` is the logical order and IDs distinguish rows when revisions repeat. The second row gets a 1 ms `created_at` offset to keep the pair ordered in `:lagged`.
- Notifications register with `db/after-commit` inside the save transaction, not in the response hook, so a rollback is never published and a later HTTP or audit failure does not cancel a committed publication. Within one save they keep repair-before-edit order; there is no global order across transactions. `wrap-audit` runs after commit and its SQLSTATE 57014 answers the same 504 `:statement-timeout` as a cancellation inside the save even when the file committed. Neither a timeout nor a lost response proves the write rolled back.

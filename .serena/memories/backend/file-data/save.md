# File save acceptance

- Start at `app.rpc.commands.files-update`; for client handling and retry see `mem:frontend/workspace-state-persistence-subtleties`, and for version and fragment lifetime see `mem:backend/file-data/reads-and-versions`.
- Partial acceptance requires `:changes-with-metadata` with a `:commit-id` on every group. Flat changes or groups without IDs remain all-or-nothing. Try the entire batch first: a later commit may repair an earlier one. On a change failure, `apply-commits` searches for an accepted prefix and returns HTTP 200 with a `:rejected` suffix. `:preexisting-damage` means the data touched by the first rejected commit already failed validation on the base before that commit.
- Persist and broadcast only the accepted prefix. A fully rejected save does not write a revision, change `revn`, or broadcast file changes. Database, I/O, interruption and missing-fragment errors fail the request rather than reject a commit. `app.http.errors` distinguishes transient failures the client can retry from permanent errors; do not classify every I/O error as transient.
- Each `apply-prefix` attempt starts from the original file, resets pointer tracking to its baseline and clears media-reference state. Keep only the accepted attempt's tracked pointers and references. A pointer already marked modified can retain its ID across edits, so leaking failed tracking can persist the rejected version under an accepted ID.
- Prefer the `fdata/with-*` wrappers for pointer loading and tracking. The save path toggles tracking within the same atom for validation and repair; do not replace that with a fresh tracking scope. Under schema validation, decode affected objects on the shared base before attempts so derived maps inherit the cache. Validation timings describe the first attempt; the bisection has its own retry timing. For controlled save failures, see `:debug-save-faults` in `app.rpc.commands.files-update`.

# File save acceptance

- Start at `app.rpc.commands.files-update`; for client handling and retry see `mem:frontend/workspace-persistence`, and for version and fragment lifetime see `mem:backend/file-data/reads-and-versions`.
- Partial acceptance requires named commits: `update-file-v2` sends `:commits` with a `:commit-id` on every entry (schema enforced), and the deprecated `update-file` uses `:changes-with-metadata` groups that all carry one. Flat changes or groups without IDs remain all-or-nothing. Try the entire batch first: a later commit may repair an earlier one. On a change failure, `apply-commits` searches for an accepted prefix and returns HTTP 200 with a `:rejected` suffix. `:preexisting-damage` means the data touched by the first rejected commit already failed validation on the base before that commit.
- Persist and broadcast only the accepted prefix. A fully rejected save does not write a revision, change `revn`, or broadcast file changes. Database, I/O, interruption and missing-fragment errors fail the request rather than reject a commit. `app.http.errors` distinguishes transient failures the client can retry from permanent errors; do not classify every I/O error as transient.
- Each `apply-prefix` attempt starts from the original file, resets pointer tracking to its baseline and clears media-reference state. Keep only the accepted attempt's tracked pointers and references. A pointer already marked modified can retain its ID across edits, so leaking failed tracking can persist the rejected version under an accepted ID.
- Prefer the `fdata/with-*` wrappers for pointer loading and tracking. The save path toggles tracking within the same atom for validation and repair; do not replace that with a fresh tracking scope. Under schema validation, decode affected objects on the shared base before attempts so derived maps inherit the cache. Validation timings describe the first attempt; the bisection has its own retry timing. For controlled save failures, see `:debug-save-faults` in `app.rpc.commands.files-update`.
- A written revision stores its payload in `file_data` (`type = 'revision'`) with the same id and deletion date as its `file_change` row. The editor now sends only `:commit-id` and forward `:changes` per commit; the closed schema rejects commit-level `:redo-changes`/`:undo-changes` and the legacy top-level keys. The payload is `{:redo-changes [...] :undo-changes []}` with the accepted prefix in edit order: the empty list means no inverse was stored. Local redo and undo stay in the editor; the server neither receives undo nor computes an inverse, and older payloads are not rewritten. The count of rejected commit IDs gives the rejected suffix length, not a change count; a retry after a lost response can write another revision. The deprecated `update-file` remains for old clients.
- Each save writes a new payload row, so `fdata/upsert!` passes `:storage-object-id nil`. `file_change.changes` still carries the accepted redo for readers deployed before the payload existed; a later step reads the payload with a fallback to the column and stops writing it.
- The editor opts in with `:repair-in-response true`. v2 answers the pre-save `:revn`/`:vern`, the attempt's ordered `:written` rows (`id`, `revn`, `kind`) and `:saved-revn` only after a write; it has no `:lagged`. `:repair {:id :revn :changes}` is inline only for edit→repair, and a relinking fallback answers `:media-relinked true` with `:saved-revn` and no `:repair`. `:recovery` is an exact bounded predecessor interval used for proof, not a reason to read when the whole interval is proven; `:edit-matches-request` ties a complete edit to submitted redo, not replay safety. Edit-before-repair is allowed only after proving the legacy repair-before-edit control: initial errors must match entities and occurrences, or the edit must leave data unchanged. Ambiguous details, pending migrations and media refs that may be relinked keep the legacy order.
- A repair save writes two revision rows and payloads with the same deletion schedule; neither row stores an inverse. The edit is the row linked from audit. `revn` is the logical order and IDs distinguish rows when revisions repeat. The second row gets a 1 ms `created_at` offset to keep the pair ordered in the v1 `:lagged` answer.
- Notifications register with `db/after-commit` inside the save transaction, not in the response hook, so a rollback is never published and a later HTTP or audit failure does not cancel a committed publication. Within one save they keep repair-before-edit order; there is no global order across transactions. `wrap-audit` runs after commit and its SQLSTATE 57014 answers the same 504 `:statement-timeout` as a cancellation inside the save even when the file committed. Neither a timeout nor a lost response proves the write rolled back.
- `:file-change-retention` is off by default. When enabled, the shared save writer marks each new revision row with `file_change.retained` and its payload with boolean `retained` metadata, both with `deleted_at = NULL`; pair them by `(file_id, id)`, not `kind` or nullability. The file trash job dates both, a valid restore clears both, and GC checks the file deadline and lock before deleting either row even when the flag is later off. Offload carries the metadata and pointer with the same payload ID.
- Catch-up stays off until all semantic writers, restore boundaries, retention and the save backlog contract are verified; no production writer establishes the boundary yet. Eligible payloads carry `catch-up-vern` and `catch-up-redo-sha256`, bound to the exact bytes in `file_change.changes`. Candidate counting stops at 129 and rejects above 128, redo transfer is gated in SQL at 4 MiB and decoding accepts at most 16 MiB uncompressed; the digest lets the decoder trust allocation lengths, and rows older than 24 hours are refused even when retained. The first replay allowlist is an ordinary complete edit with one page-leaf name change on a proven compatible base; migrations, repairs, relinks, partial rejections and library edits cannot receive the proof.

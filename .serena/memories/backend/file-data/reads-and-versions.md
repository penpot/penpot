# File reads, fragments and versions

- Start at `app.binfile.common/get-file` for reads, `app.features.fdata` for fragments, and `app.features.file-snapshots` and `app.rpc.commands.files-snapshot` for versions. For blob ownership see `mem:backend/file-data-storage`; for save acceptance see `mem:backend/file-data/save`.
- Keep the common read path to one file-row read plus migration resolution. If a migration may need persistence, re-read with `FOR UPDATE` and recheck on the fresh row so migration cannot overwrite a concurrent save. Read-only migration is in memory. A data read cannot request `FOR SHARE`: upgrading competing shared locks to `FOR UPDATE` can deadlock. See the `get-file` docstring for the option contract and `mem:common/file-migrations` for migration IDs and ETags.
- Fragment rows are immutable once written. Reattach unchanged pointers when persisting migrated data so unchanged pages keep their IDs. Do not materialize untouched pages just to wrap objects maps; a migration explicitly enabling `fdata/objects-map` must rewrite the pages instead. Use `fdata/realize` when the caller needs complete in-memory data.
- Snapshots share fragment rows with the live file. `file-gc` marks a fragment only when neither the live file nor any unpurged snapshot references it. Snapshot creation holds the exclusive file-row lock through insertion to serialize with saves and GC. Snapshot reads resolve fragments by live file ID. The internal loader can still read marked fragments until `objects-gc` purges them; the public fragment RPC cannot.
- A save captures its automatic snapshot before applying pending migrations. Preview migrates a version in memory using the live libraries without rewriting the historical payload; restoring a pre-migration version leaves the next read to migrate it. Manual snapshot creation and restore backup read with migration enabled. Keep applied migrations as an ordered set; for old snapshots without that set, preview and restore use different baselines and can disagree.
- Snapshot metadata lives in `file_change`, with its payload in `file_data`. Use `label IS NOT NULL` to select versions, not the legacy payload or `kind` columns; that filter also keeps revision rows out of version paths. Keep version quota predicates aligned with the partial index `file_change__user_snapshots__idx`. A revision has a matching `file_data` payload (`type = 'revision'`) with the same id and deletion date and is born dated for deletion. Restore unmarks only durable snapshots, since no later pass assigns a revision or its payload a new deletion date. The audit `:file-change-id` points to the revision, not the snapshot; see `mem:audit-log`.
- The `internal/repair/<revn>` snapshot keeps the state before both rows of a repair save. A verified opt-in edit-before-repair save can share its original fragment pointers instead of resolving untouched pages; a legacy-order repair without that snapshot materializes its original data.
- With `:file-change-retention`, a revision row and its `file_data` payload form a pair keyed by `(file_id, id)`, not by `kind` or nullability. The file trash job dates both, a valid restore clears both, and ordinary trash keeps existing snapshot and ephemeral deadlines. `objects-gc` checks the file deadline and takes its lock before deleting either retained row, even if the flag is later off.
- Catch-up reads `file_data` metadata only; a main row needs an explicit `catch-up-boundary` map (`genesis` with `vern` zero or `restore` with current `vern` and positive `revn`). `since` cannot precede that boundary, and `vern = 0` alone is not proof because restore can pick it randomly. See `mem:backend/file-data/save` for the proof and byte limits.

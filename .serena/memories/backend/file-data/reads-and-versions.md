# File reads, fragments and versions

- Start at `app.binfile.common/get-file` for reads, `app.features.fdata` for fragments, and `app.features.file-snapshots` and `app.rpc.commands.files-snapshot` for versions. For blob ownership see `mem:backend/file-data-storage`; for save acceptance see `mem:backend/file-data/save`.
- Keep the common read path to one file-row read plus migration resolution. If a migration may need persistence, re-read with `FOR UPDATE` and recheck on the fresh row so migration cannot overwrite a concurrent save. Read-only migration is in memory. A data read cannot request `FOR SHARE`: upgrading competing shared locks to `FOR UPDATE` can deadlock. See the `get-file` docstring for the option contract and `mem:common/file-migrations` for migration IDs and ETags.
- A locked payload read takes `FOR UPDATE` on the `file` row alone and reads the joined payload in a separate statement on the same connection: under `READ COMMITTED` a joined locking statement can return the latest `file` tuple with the old `file_data` tuple. Do not fold the two statements back together. A lock skipped by `:skip-locked?` never reaches the payload read; an unlocked read that finds a pending migration repeats through the locked path and rechecks on fresh data. Only the fresh payload is decoded.
- Fragment rows are immutable once written. Reattach unchanged pointers when persisting migrated data so unchanged pages keep their IDs. Do not materialize untouched pages just to wrap objects maps; a migration explicitly enabling `fdata/objects-map` must rewrite the pages instead. Use `fdata/realize` when the caller needs complete in-memory data.
- Snapshots share fragment rows with the live file. `file-gc` marks a fragment only when neither the live file nor any unpurged snapshot references it. Snapshot creation holds the exclusive file-row lock through insertion to serialize with saves and GC. Snapshot reads resolve fragments by live file ID. The internal loader can still read marked fragments until `objects-gc` purges them; the public fragment RPC cannot.
- Callers of `fsnap/create!` supply the transaction that commits snapshot metadata and payload together; the restore backup commits separately even if the restore fails. There is no audit callback in the writer: the index uses the existing save and manual snapshot RPC events as file-level signals and finds any other retained rows during its scan.
- A save captures its automatic snapshot before applying pending migrations. Preview migrates a version in memory using the live libraries without rewriting the historical payload; restoring a pre-migration version leaves the next read to migrate it. Manual snapshot creation and restore backup read with migration enabled. Keep applied migrations as an ordered set; for old snapshots without that set, preview and restore use different baselines and can disagree.
- Snapshot metadata lives in `file_change`, with its payload in `file_data`. Use `label IS NOT NULL` to select versions, not the legacy payload or `kind` columns. Keep version quota predicates aligned with the partial index `file_change__user_snapshots__idx`. Revisions are temporary and exist only in `file_change`: they are born dated for deletion. Restore unmarks durable snapshots, never revisions, since no later pass assigns a revision a new deletion date. The audit `:file-change-id` points to the revision, not the snapshot; see `mem:audit-log`.
- `file-fragments-gc` marks only prepared live fragment IDs. Preparation uses its own read-only `REPEATABLE READ` transaction and requires complete `file_change` coverage; a gap enqueues the file-level scheduler and requests a bounded worker retry. Queued indexing is not coverage, and finishing it does not schedule marking. Each marking lot owns a `READ COMMITTED` transaction. Revalidation after `FOR UPDATE SKIP LOCKED` checks the live revision, the tuple identities of the file and canonical main, and whether new IDs appeared at that revision; it uses a new statement, not the preparation snapshot. Both phases use `db/tx-run!` and set isolation before reading. Inactivity checks `modified_at` independently of the safety checks. Both the consumer and the handler check `:feature-fdata-pointer-map` directly; offload keeps its skip-on-lock behavior. Indexing rules: `mem:backend/file-data-storage`.
- Preparation that finds no live canonical row for a live file raises `:missing-main-file-data` without marking and never falls back to legacy content. An existing canonical row is not enough: if its payload is still absent after resolution and decoding, fragment GC raises `:invalid-main-payload` before candidate selection. An empty pointer set from a present payload is valid.
- The `file-fragments-gc` result schema restores the status keyword and the required file UUID on read. New results require `marked`: the count already committed in this run, even when a later lot stopped marking, or zero when nothing was marked. `:gone` means the file is no longer live; it is distinct from a live file missing its main row. A completed run that filled the candidate limit schedules fresh preparation because it cannot tell whether more unmarked fragments remain. Incomplete coverage requests a retry instead of returning a result.

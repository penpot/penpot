# GitHub Actions configuration traps

- A workflow using `pull_request_target` must be listed in an applicable repository Actions event policy that allows every event the workflow uses (for example `pull_request_target` and `workflow_dispatch`). GitHub's default policy blocks `pull_request_target` in public repos: it is in evaluate mode until 2026-12-02 and then becomes active, so an unwlisted workflow keeps running now but stops later.
- List policies with `gh api -H "X-GitHub-Api-Version: 2026-03-10" 'repos/penpot/penpot/actions/policies?per_page=100'`. The list omits `conditions` and `rules`; read each policy with `.../actions/policies/<id>` before deciding where to add a workflow path. Edit repository settings only with explicit authorization.
- `pull_request_target` takes the workflow file from the default branch (`develop`), not from the pull request base. A workflow must be merged into `develop` before it can run for pull requests targeting other branches; `workflow_dispatch` is also only available for workflows on the default branch. No backport to release branches is needed for this event.
- The triage workflows mint a GitHub App token from `TRIAGE_APP_CLIENT_ID` and `TRIAGE_APP_PRIVATE_KEY`. They are organization secrets, so `gh secret list --repo penpot/penpot` does not show them. The App already has repository `issues: write` and `pull-requests: write`, plus organization `projects: write` and `members: read`.
- An issue closed with `GITHUB_TOKEN` does not trigger `issues-triage.yml` (or `auto-label.yml` on `develop`). Use the App token for any workflow whose close must move the Main board card.

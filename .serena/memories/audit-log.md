# Audit events

- Entry points: `app.loggers.audit` for emission and filtering, `app.rpc` for the RPC wrapper, `app.rpc.commands.audit` for browser ingest and discovery, `app.rpc.management.nitrate` for trusted service ingest, and frontend `app.main.data.event` for collection. Delivery, cursor ordering and retention: `mem:backend/audit-consumers`.

## Trust and emission

- Attribute the event to the actor, not an arbitrary profile in the response (e.g. an inviter when the invitee acted). For RPC results, set `::audit/profile-id` only after establishing the actor; hand-built events must pass a UUID since they bypass wrapper normalization. Use `uuid/zero` only when the actor is unknown.
- Browser ingest derives the actor from the session, never the event. Public `x-client` can influence `:initiator`; it is not an authorization signal. On backend RPCs `:initiator` comes from the authenticated shared-key context or defaults to `"app"`. Trusted management ingest authenticates the service and accepts the actor it reports; that does not prove the remote business operation and the audit event committed together.
- `source` identifies the channel, not the outcome. A browser event can be lost on shutdown, overflow or failure; HTTP success can mean an ingest error was logged rather than rows persisted. Do not use missing browser events as evidence that an action did not happen. Avoid browser copies of backend actions unless the UI observes something distinct; respect `skip-audit?` on resumed gestures.
- `audit/submit` propagates failures. The RPC wrapper may emit **after** the business transaction commits, so a failed audit response does not prove the mutation rolled back. When explicitly submitting inside a transaction, the failure can roll back the mutation with the event. `audit/insert` alone writes full rows; it does not fan out.
- The `:import-binfile` job submits `import-binfile` from its terminal hook in the transaction that records `completed`, `failed` or `cancelled`. Its props explicitly select `project-id`, `name`, `version`, `generated-by` and `referer` from job params, then add `job-id`, `team-id`, `status` and completed file ids/count; new job params do not automatically reach audit. New jobs freeze `team-id` at creation and both creation and terminal events use it for webhook routing; older jobs without it resolve the current project team as fallback. A queued cancellation also emits it; dispatcher-side `aborted` does not. The hook has no request context and omits handler-only elapsed time and package size. Import files commit earlier, and the `create-file` events use a separate transaction after that commit: a later audit or terminal failure cannot roll the files back, and a cancellation that wins late can coexist with committed files. The `job-id` joins the outcome to the job-creation event.
- `props` describes the action, `context` describes capture. Do not put secrets in either, including on paths that bypass the RPC wrapper's partial sanitization. `:client-event-origin` on backend RPCs explains the UI entry point; it is not the browser event's `:event-origin` or a substitute for business fields.

## Projection contracts

- Emit the entity and scope IDs receivers need instead of assuming access to production tables. A create needs the new entity's ID; moves need source and destination team IDs; deletes need affected IDs before rows disappear. For bulk paths that bypass per-entity emission, use the create-event helpers in `app.loggers.audit`. An existing membership conflict is not a creation event; keep the actor separate from the member.
- Preserve `:file-id` and the resolved `:team-id` on `file-gc` trim events. `delete-object-with-cascade` carries flat `:team-ids` alongside the nested `:cascade` map so receivers can route the event without joining production tables.
- An `update-file` event can describe a successful, partial or rejected save. Only saved changes have `:file-change-id`; it points to the revision, not the previous-state snapshot. The reference index consumer only needs `props.id` (the file) and the outcome. Read it with `::db/remove-deleted false` because it already has a future deletion date. Even then GC may have removed it.
- `create-file-snapshot` already carries `props.file-id` in its ordinary RPC audit event; neither this command nor `fsnap/create!` needs to emit the snapshot ID. There is no dedicated event for automatic snapshots, restore backups or SREPL writes. The file-level scan finds retained history even without an event for a particular row; see `mem:backend/file-data-storage`.
- Preserve explicit business props that receivers depend on, including direct versus team organization invitations. `backend-tests.rpc-audit-test` and `backend-tests.rpc-team-test` cover emission and attribution. Assert exact matching event counts so duplicate emissions cannot pass.

## Destinations and privacy

- Full rows and telemetry shadows are independent. Telemetry filters props and context and reduces time and IP detail before storage, but keeps a stable profile UUID. Treat it as reduced data, not anonymous data; inspect `filter-telemetry-props` and `filter-telemetry-context` and their tests before adding fields. If public ingest stores both copies, they commit together.
- `:audit-log` in discovery is a wire signal for full-row persistence or error reporting, not a configurable flag. `:telemetry` is independent. Error reporters can receive browser crashes without stored audit rows; see `mem:frontend/error-reporting` for bounded reports and classification. A single oversized report can block later rows in a chunk.
- Webhooks are jobs, not cursor consumers. Debounce delivers the last payload in a burst, not a batch of payloads. Delivery failure updates the webhook and its delivery log, not the origin event. Trigger events can refer to the producer's full-row ID when it exists; telemetry copies have their own IDs.
- The local `file-change` consumer (ID `5`, metrics label `file-change-refs`) is permanent on writable workers and turns effective saves and manual snapshots into file-level indexing signals. It accepts only authenticated Penpot backend events; delivery, filtering and GC scheduling rules live in `mem:backend/audit-consumers`.

# File changes and undo

- File changes are both the persistence payload and the basis for undo. Use the production change pipeline rather than editing object maps directly. Start in `app.common.files.changes` for schemas and application, `app.common.files.changes-builder` for redo/undo construction, and `app.common.files.changes-merge` for compaction.
- Compaction must preserve redo and undo order: merge `:reg-objects` per container and put the registrations after the changes that resize the children. Never compact across commit boundaries; the backend can reject individual commits by `commit-id`. See `mem:frontend/workspace-state-persistence-subtleties` for the save order.
- Don't send a deleted component's entire object map with a metadata-only edit. Scope shape edits to `:component-id` using the builder's container context. In component metadata, omitted `:objects` preserves stored shapes; explicit nil clears them. Reserve `:objects? true` for repairs that intentionally move or clear the whole map.
- Apply fixture edits through `app.common.test-helpers.files/apply-changes` so tests exercise the production applier. Disable fixture validation only for intentionally invalid intermediate states. See `mem:common/testing`.
- For touched groups see `mem:common/component-data-model`; for the second pass see `mem:common/change-application` and for validation see `mem:common/file-validation`. For live inspection of emitted changes, see `mem:common/component-debugging-recipes`.

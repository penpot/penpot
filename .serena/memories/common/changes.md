# File changes

- File changes are both persistence payloads and the basis for undo. Start at `app.common.files.changes` for schemas and application, `app.common.files.changes-builder` for redo/undo construction and `app.common.files.changes-merge` for compaction. Use the production pipeline rather than editing object maps directly.

## Construction and compaction

- Preserve redo and undo order when compacting: merge `:reg-objects` per container and place registrations after changes that resize children. Never compact across commit boundaries; the backend can reject individual commits by `commit-id`. Client save ordering is in `mem:frontend/workspace-persistence`.
- Do not send a deleted component's entire object map for a metadata-only edit. Scope shape edits to `:component-id` using the builder's container context. Omitted `:objects` preserves stored shapes; explicit nil clears them. Reserve `:objects? true` for repairs that intentionally move or clear the whole map.
- For fixture edits and validation controls see `mem:common/testing`.

## Save payloads

- The editor saves through `update-file-v2`: `:commits` in edit order, each with only `:commit-id` and a vector of forward `:changes`. The closed schema rejects `:redo-changes`, `:undo-changes`, flat top-level `:changes` and `:changes-with-metadata`. `file_change.changes` and the `file_data` revision payload hold the accepted prefix in edit order; the payload shape is `{:redo-changes [...] :undo-changes []}`, where the empty list means no inverse was stored, not that applying an empty undo is meaningful. Local redo and undo stay in the editor for rebase, rollback and Ctrl+Z; the server never receives undo and computes no inverse, and older payloads are not rewritten. The deprecated `update-file` remains for old clients with `:lagged` in timestamp order; v2 confirms exact revision IDs and bounded recovery metadata instead. The current editor never falls back to v1, and a full read after confirmation must not replay the confirmed edit. See `mem:backend/file-data/save` for prefix selection.
- The editor opts in with `:repair-in-response`. When the server proves edit-before-repair it stores consecutive edit and repair revisions with the automatic snapshot before both; the two redo lists in revision order reconstruct the stored file, and neither row stores an inverse. Otherwise it keeps repair→edit and announces the repair over WebSocket; if that fallback relinks images, the edit redo carries the final refs. An automatic repair is never an editor undo entry. Exact inverse generation against server state, deduplication of repeated POSTs and undo-history recovery on reload are separate contracts.

## Application and schema validation

- `process-changes` validates the change vector once by default, reduces it and then processes collected touched changes; `verify? false` is for callers that already validated. `:set` delegates to `ctn/set-shape-attr`, while `:assign` decodes attrs before per-attr sets. Component touched and copy rules are in `mem:common/components`.
- `:restore-component` restores only the component record: it removes `:objects` and `:deleted`, optionally updates the main instance page, and takes a variant's `:variant-id` from the existing main shape. `prepare-restore-component` generates separate `:add-obj` changes before it to restore the shape tree. Affected-file validation conservatively selects the referenced page for the restore operation itself.
- `shape-tree/add-shape` falls back invalid parents or frames to root and keeps parent `:shapes` a vector without duplicate IDs. `delete-shape` removes descendants from the objects map as well as unlinking the parent; render-wasm deletion has different undo internals.
- Page-object maps can carry metadata indexes. Rebuild them with `start-page-index` / `update-page-index` as appropriate; frontend commit application calls `ctst/update-object-indices` after page changes.
- `update-file` and `update-file-v2` share change-scoped redo validation: `touched-page-ids` selects pages while non-page data is checked whole. In v2, malformed change records fail request validation with `:params-validation` before any commit is considered for partial acceptance; the request carries no undo. Register new change types as page-writing or file-level; unknown types fall back to the full schema check, which loads every page. Referential integrity and repair are in `mem:common/components`.

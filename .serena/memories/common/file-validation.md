# Common file validation and repair

- Start at `app.common.files.validate` and `app.common.files.repair`. Full referential and semantic validation runs when file features include `"components/v2"`; it visits the root and orphan shapes, then component records. `validate-file!` raises `:validation` / `:referential-integrity` with details.
- `update-file` uses change-scoped referential and schema validation. `touched-page-ids` selects pages for the schema check while non-page data is checked whole. Register a new change type as page-writing or file-level; an unknown type falls back to validating the whole file, which loads every page.
- `repair-file` produces redo changes rather than mutating data; callers must apply or persist them. `repair-file-until-valid` stops on no errors, unchanged data, a stable error fingerprint without `:shape`, or its iteration limit. Check the fingerprint before another repair pass; backend `PointerMap` equality is pointer identity. Multiple `:set` repairs on one shape can require multiple passes because each repair starts from the original file data.
- For `:ref-shape-not-found`, repair can restore a local component's `:main-instance-id` when the recorded main is missing but the matching main exists on its recorded page. Otherwise it tries a near-main reassignment or detaches the copy subtree.
- `:missing-slot` is a real swap only when a copy sub-head's `shape-ref` is no longer a child of the near main parent. A sibling in a different position is a reorder, not a swap: assigning a slot would block normal component sync. Migration 0019 follows the same membership rule; see `mem:common/file-migrations`.
- For change application see `mem:common/change-application`; for copy and slot semantics see `mem:common/component-data-model`.

# Consumer generalization: out-of-band migration

Procedure for a large instance, to run **before upgrading** to the release
that ships the audit-log cursor consumers and the jobs substrate.

- Migration: `backend/src/app/migrations/sql/0159-consumer-generalization.sql`
- Issue: <https://github.com/penpot/penpot/issues/12700>

## When you need this

The migration runner executes every pending step in a single transaction. On an
instance with a large `audit_log` or `job` table the plain index builds hold a
`SHARE` lock for the whole build and every `ALTER` keeps its `ACCESS EXCLUSIVE`
until that one commit, so writes stall for minutes. Pre-apply the same
statements out of band, outside a transaction block, in this order, and register
the steps before you start (step 0). This procedure covers
`0159-consumer-generalization` and the `0154-add-job-table` step it depends on
when you come from 2.19.

Pre-applying does not make the migration free by itself: the guards
(`IF NOT EXISTS`, `seq IS NULL`) skip the work, not the locks. Registering the
step is what makes the runner skip the group.

**The application keeps writing to `audit_log` for the whole procedure.** Do
not stop the web instances. The DDL takes a brief `ACCESS EXCLUSIVE`
(metadata-only) that `lock_timeout` bounds; the index builds use
`CONCURRENTLY`; the backfill takes row locks only. Stopping the archiver and its
GC is fine; stopping the writes is not.

While the new version runs, the consumers read only rows below
`pg_snapshot_xmin(pg_current_snapshot())`, the oldest transaction of the whole
database: a long write transaction (a binfile import runs in one for up to 30
minutes) pauses archiving and the GC until it commits, and a slow destination
does too, because a chunk sends inside its transaction and holds the cut back
until it ends. Nothing is lost and the lag gauge shows it; it is not a stuck
consumer.

## Session settings

Run every block below in a session with these two settings. They are plain SQL
(no `psql` meta-commands), so any client accepts them, and they last for the
session: if you paste a block into a new session, run them first.

```sql
SET statement_timeout = 0;
SET lock_timeout = '5s';
```

`statement_timeout = 0` keeps a client's default from killing the backfill or
the `CONCURRENTLY` builds. `lock_timeout = '5s'` makes an `ALTER` that waits
behind a long transaction fail and be retried, instead of queueing in front of
every later query on the table. Both are safe to repeat.

## 0. Register the steps first

```sql
INSERT INTO migrations (module, step)
VALUES ('main', '0154-add-job-table'),
       ('main', '0159-consumer-generalization')
ON CONFLICT (module, step) DO NOTHING;

SELECT module, step FROM migrations
 WHERE module = 'main'
   AND step IN ('0154-add-job-table', '0159-consumer-generalization')
 ORDER BY step;
```

These rows are what make the out-of-band run worth it. Without them, the
runner finds the pre-applied schema and runs the statements again: the guards
skip the work, not the `ACCESS EXCLUSIVE` of each `ALTER` nor the backfill
scan.

Registering first is the safe order for the locks: from this moment the runner
never touches the group, whatever deploy lands while you work. The other side
of the deal is that the steps below become the only thing that applies the
schema, so finish them **before you deploy the new version**.

The insert is unconditional: a database that already has the table still gets
its row here, and the select answers two rows either way.

## 1. Stop the legacy archiver and its GC, then delete what it archived

Turn off the old archiver and its garbage collection with their flags:
`:audit-log-archive` off and `:audit-log-gc` off. Keep `:audit-log` on. The
new version uses `:audit-log-gc` for its own GC, so the same flag keeps both
off during the rollout. Keep `:nexus` and `:admin-console` on for the new
consumers; the old version ignores both (its flag parser keeps unknown names
in the set and no old code reads them). Roll the old workers with the flags
off (the web instances keep writing; the other jobs keep running) and wait for
the active archive and GC tasks to finish. The old and new versions do not serialize
each other: a concurrent old archiver can mark and send rows the new producer
wrote, and the old GC can delete rows the new consumers have not read yet.

Then delete the rows the old archiver had already archived, so the replay
does not send them to Nexus again. They are the rows the old GC would delete
anyway. Check the column first (a pre-release database that ran the pending
queue does not have it):

```sql
SELECT 1 FROM information_schema.columns
 WHERE table_name = 'audit_log' AND column_name = 'archived_at';
```

If it answers a row, delete in batches (repeat until the statement removes
no rows):

```sql
DELETE FROM audit_log
 WHERE id IN (SELECT id FROM audit_log
               WHERE archived_at IS NOT NULL
               LIMIT 5000);
```

Do **not** drop `archived_at` or the indexes that served it
(`audit_log__created_at__idx`, `audit_log__archived_at__idx`,
`audit_log_id_archived_at_idx`). The old archiver may still be running on an
instance that has not been replaced, and a later release removes them. The
consumers order by `(xid, seq)` (step 5); telemetry keeps
`audit_log__source__created_at__idx` plus a sort.

## 2. Pre-apply the jobs step when coming from 2.19

2.19 does not have the `job` table: `0154-add-job-table` creates it and is
new in this release. Step 0 already registered the step, so the runner will
never apply it. Check whether the table exists:

```sql
SELECT to_regclass('public.job') AS job;
```

If it answers a row, nothing to do here: the schema and the registration row
are both in place. If it answers null, apply
`backend/src/app/migrations/sql/0154-add-job-table.sql` out of band (plain
SQL, outside a transaction block; the tables are new and empty). The file is
the whole step, not just the tables: `job` with its six indexes (dispatcher,
orphan, profile, resource, expires, retention), `job_event` with its history
index, and the `deletion_protection__tgr` trigger. Step 8 checks every one of
them.

Both rows of step 0 matter: registering `0154` keeps the runner from
re-creating a table you just created, and registering `0159` is what forces
step 7 to apply the job columns and indexes by hand instead of leaving them
to the runner. The old version does not use the `job` table; the new one
inserts into it from the web path (`jobs/submit`), so it cannot boot without
this.

The file runs outside a transaction, so a failure halfway leaves the tables
without the rest of their objects and re-running the file fails on
`CREATE TABLE job`. The gate lists which objects are missing: create only
those by hand.

## 3. Audit log: columns, reserved range, defaults, backfill

Columns first (metadata-only), the reserved low range and the defaults the
old web instances need immediately: they keep inserting while the DDL and the
backfill run, and the database fills the new columns for them. The old code
ignores them.

```sql
CREATE SEQUENCE IF NOT EXISTS audit_log_seq_seq;
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS seq bigint;
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS xid xid8 NOT NULL DEFAULT '0'::xid8;
ALTER SEQUENCE audit_log_seq_seq OWNED BY audit_log.seq;

-- Reserve the low range for the history: new rows start above the backfill.
-- Only on the first application: a sequence that already left 1 is reserved
-- by the operator or in use, and a re-run must not move it.
SELECT setval('audit_log_seq_seq',
              (SELECT count(*) + 1000000 FROM audit_log),
              false)
 WHERE (SELECT last_value FROM audit_log_seq_seq) = 1
   AND NOT (SELECT is_called FROM audit_log_seq_seq);

ALTER TABLE audit_log ALTER COLUMN seq SET DEFAULT nextval('audit_log_seq_seq');
ALTER TABLE audit_log ALTER COLUMN xid SET DEFAULT pg_current_xact_id();
```

Then the backfill. It is one statement, it takes row locks only (never a table
lock), and it filters `seq IS NULL`, so it can be interrupted and re-run. The
archiver is stopped, but the web instances keep inserting; their new rows get
`seq` from the default, so the backfill only touches the history. It sorts by
`(created_at, id)`: the `(created_at, id)` index this branch used belonged to
the pending queue and never shipped. On a large table, raise `work_mem` for the
session before running it so the sort stays in memory:

```sql
UPDATE audit_log
   SET seq = ordered.rn
  FROM (SELECT id, row_number() OVER (ORDER BY created_at, id) AS rn
          FROM audit_log
         WHERE seq IS NULL) ordered
 WHERE audit_log.id = ordered.id;
```

## 4. Audit log: `seq` and `source` NOT NULL without a long `ACCESS EXCLUSIVE` scan

No row can be `NULL` in `seq` here: the default was set in step 3. `source` is
nullable since `0064`; fill what is left first.

```sql
ALTER TABLE audit_log ADD CONSTRAINT audit_log__seq__not_null
    CHECK (seq IS NOT NULL) NOT VALID;
ALTER TABLE audit_log VALIDATE CONSTRAINT audit_log__seq__not_null;
ALTER TABLE audit_log ALTER COLUMN seq SET NOT NULL;
ALTER TABLE audit_log DROP CONSTRAINT audit_log__seq__not_null;

UPDATE audit_log SET source = 'backend' WHERE source IS NULL;

ALTER TABLE audit_log ADD CONSTRAINT audit_log__source__not_null
    CHECK (source IS NOT NULL) NOT VALID;
ALTER TABLE audit_log VALIDATE CONSTRAINT audit_log__source__not_null;
ALTER TABLE audit_log ALTER COLUMN source SET NOT NULL;
ALTER TABLE audit_log DROP CONSTRAINT audit_log__source__not_null;
```

## 5. Audit log: cursor index and cursor table

The index with `CONCURRENTLY`, and the cursor table, which starts empty:

```sql
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS audit_log__xid__seq__idx
    ON audit_log (xid, seq);

CREATE TABLE IF NOT EXISTS audit_log_consumer_cursor (
  consumer   smallint    NOT NULL,
  xid        xid8        NOT NULL,
  seq        bigint      NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer));
```

Do not seed it. The migration cannot know which consumers are enabled, so a
consumer with no row creates its own at `(0, 0)` on its first pass
(`ensure-cursor`), below any real position: that pass drains the buffer the
rollout left, i.e. the unarchived backlog. The GC treats a missing cursor as
position 0 and deletes nothing until the consumer creates it, so the replay
cannot race a delete.

## 6. Old queue: drop its foreign key (pre-release databases only)

The release never creates `audit_log_pending`: the pending queue that would
have used it never shipped. A pre-release database that ran that step may still
have the table and leftover rows; dropping the foreign key keeps them inert, so
the new GC cannot fail on the rows they reference:

```sql
ALTER TABLE IF EXISTS audit_log_pending
    DROP CONSTRAINT IF EXISTS audit_log_pending_audit_log_id_fkey;
```

## 7. Jobs

The two columns and the two unique indexes, the indexes with `CONCURRENTLY`:

```sql
ALTER TABLE job ADD COLUMN IF NOT EXISTS exclusive boolean NOT NULL DEFAULT false;
ALTER TABLE job ADD COLUMN IF NOT EXISTS dedupe    boolean NOT NULL DEFAULT false;

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS job__live_exclusive__uniq
    ON job (tenant, name, queue, label)
    WHERE exclusive AND status IN ('new', 'scheduled', 'running', 'retry');

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS job__new_dedupe__uniq
    ON job (tenant, name, queue, label)
    WHERE dedupe AND status = 'new';
```

The lost sweep index changes shape: it filters by `modified_at`, not by
`scheduled_at`. `job` is not in production yet, so a plain rebuild is enough:

```sql
DROP INDEX IF EXISTS job__scheduled__idx;
CREATE INDEX IF NOT EXISTS job__scheduled__idx
    ON job (tenant, modified_at)
 WHERE status = 'scheduled';
```

The migration body cannot use `CONCURRENTLY` (the runner applies it in one
transaction), which is why the out-of-band copy does; on `job`, which is not in
production yet, either form builds instantly.

If an early `0154` built the cron probe index, drop it too (the submit resolves
the overlap at insert time now):

```sql
DROP INDEX IF EXISTS job__name_label__idx;
```

## 8. Gate before deploying

Lock hygiene: every `ALTER` waits for `ACCESS EXCLUSIVE`, so run the blocks
with the `lock_timeout` from [Session settings](#session-settings) and retry a
timed-out statement instead of letting it queue behind a long transaction. An
interrupted `CONCURRENTLY` build leaves the index `INVALID`, and
`IF NOT EXISTS` matches by name, so the migration would accept it and the
dedupe/exclusivity would stop enforcing silently. The checks:

```sql
SELECT indexname, indexdef FROM pg_indexes
 WHERE indexname IN ('job__live_exclusive__uniq',
                     'job__new_dedupe__uniq',
                     'job__scheduled__idx',
                     'audit_log__xid__seq__idx');

SELECT indexrelid::regclass AS index, indisvalid, indisunique
  FROM pg_index
 WHERE indexrelid IN ('job__live_exclusive__uniq'::regclass,
                      'job__new_dedupe__uniq'::regclass,
                      'audit_log__xid__seq__idx'::regclass);

SELECT column_name, is_nullable
  FROM information_schema.columns
 WHERE table_name = 'audit_log'
   AND column_name IN ('seq', 'xid', 'source')
 ORDER BY 1;
```

Any index with `indisvalid = false` must be dropped and rebuilt before the
deploy, and the three columns of `audit_log` must answer `NO`.

The job side is a gate too: both job tables, the cursor table, the indexes of
the check and the trigger must exist before the deploy. A half-applied `0154`
(it runs outside a transaction) or a skipped step 7 would otherwise only
surface as a boot failure.

```sql
SELECT to_regclass('public.job') IS NOT NULL AS job,
       to_regclass('public.job_event') IS NOT NULL AS job_event,
       to_regclass('public.audit_log_consumer_cursor') IS NOT NULL AS cursor;

SELECT indexname FROM pg_indexes
 WHERE tablename IN ('job', 'job_event')
   AND indexname IN ('job__dispatcher__idx', 'job__orphan__idx',
                     'job__profile__idx', 'job__resource__idx',
                     'job__expires__idx', 'job__retention__idx',
                     'job__scheduled__idx', 'job_event__job_kind_created_idx')
 ORDER BY 1;

SELECT column_name, is_nullable
  FROM information_schema.columns
  WHERE table_name = 'job'
   AND column_name IN ('exclusive', 'dedupe')
  ORDER BY 1;

SELECT tgname FROM pg_trigger
 WHERE tgrelid = to_regclass('public.job')
   AND tgname = 'deletion_protection__tgr'
   AND NOT tgisinternal;
```

The three tables must answer true, the eight indexes must be listed, the two
flags must answer `NO`, and the trigger must appear. The
`job__scheduled__idx` definition of the first check must read
`(tenant, modified_at)`, not `(tenant, scheduled_at)`: step 7 drops and
rebuilds it, and `CREATE INDEX IF NOT EXISTS` matches by name. This is a gate:
do not deploy if it fails. The catalog checks are instant; the
`CHECK NOT VALID` / `VALIDATE` / `SET NOT NULL` dance already proved there is
no NULL, so a `count(*)` would only scan the table again.

## 9. After the rollout

Once every instance runs this version, the new consumers have replayed the
unarchived buffer. Turn on `:audit-log-gc` (rolling restart of the new
workers) so the new GC deletes the rows the consumers have passed. Remove
`:audit-log-archive`; the new version does not use it.

The legacy `archived_at` column and the indexes that served it stay for a
later release, once every instance is new. A database that ran a pre-release
build with the pending queue can drop `audit_log_pending` now (its foreign key
is already gone); a released database never has it:

```sql
DROP TABLE IF EXISTS audit_log_pending;
```

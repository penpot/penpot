# 2.20.0 — Unified upgrade runbook

Single, self-contained procedure for upgrading an instance to the release
that ships:

- Partition `file_change` by `HASH (file_id)` with 16 partitions, aligned
  with `file_data`: `backend/src/app/migrations/sql/0158-partition-file-change.sql`,
  issue <https://github.com/penpot/penpot/issues/12416>.
- The file data storage pointer as a column `file_data.storage_object_id`
  with a foreign key to `storage_object(id)`:
  `backend/src/app/migrations/sql/0159-add-file-data-storage-object-id.sql`,
  issue <https://github.com/penpot/penpot/issues/12769>.
- The audit-log cursor consumers and the jobs substrate:
  `backend/src/app/migrations/sql/0154-add-job-table.sql` and
  `backend/src/app/migrations/sql/0159-consumer-generalization.sql`,
  issue <https://github.com/penpot/penpot/issues/12700>.

Migrations apply in this order at boot when they are not registered in the
`migrations` table: `0154-add-job-table`, `0158-partition-file-change`,
`0159-add-file-data-storage-object-id`, then `0159-consumer-generalization`.

**This document is self-contained and manual.** Every block is plain SQL,
paste-able into any client that speaks SQL; there are no shell scripts and no
`psql` meta-commands. It runs on PostgreSQL 15 or newer. It does not replace
`operations/2.20.0-file-change-partition.md`,
`operations/2.20.0-file-data-storage-object-id.md` or
`operations/2.20.0-consumer-generalization.md`: they stay as the reference for
their individual procedure. Where this document and those disagree, this
document wins for the unified execution; they win for the details of one
area only.

## When each phase runs

| Phase | When | Service |
|---|---|---|
| 1 | Before the upgrade; pre-flight and online preparation | 2.19.0 serving |
| 2 | The deploy to 2.20.0 | **Full stop** for the storage backfill |
| 3 | After the upgrade, 2.20.0 serving; phase 3.3 every 1-6 h for days | Online |
| 4 | **A scheduled maintenance window** for the `file_change` partition cutover | **Backend and workers stopped** |
| 5 | After the cutover | Online |

This runbook is a complete manual procedure. Follow every phase in order,
regardless of database size; do not skip steps based on how much data a table
contains. Phase 2 is a coordinated full stop of the backend and workers for
the storage backfill during the deploy. Phase 4 is a separate scheduled
maintenance window for the `file_change` partition cutover after the deploy.
The backfill runs on every instance, even when it updates no rows.

## Ordering constraints (do not rearrange)

- The migration steps are pre-registered at the beginning: the 2.20.0
  migration runner skips them, and the manual procedure below is the only path
  that applies their schema changes and backfills.
- Phases 3 and 4 need the **new code** running: it moves `updated_at` on
  every write, the watermark of the copy passes. The deploy (phase 2) goes
  before phase 3.
- The `file_data` backfill always runs in phase 2, while every old instance
  is stopped and **before** the new instances start: the old code writes the
  pointer only to `metadata.storage-ref-id`, the new code reads only the
  column. A rolling deploy in between would mix both.
- The `0158` cutover (phase 4) takes minutes in a low-traffic window. Saves
  that fall inside fail and the user retries.
- The new GC runs by default. Keep `disable-audit-log-gc` in `PENPOT_FLAGS`
  throughout the mixed-version rollout. Restore the default in phase 5.6.

### 1.3 Partition preparation

**1.3.1 Add the `kind` column to the current table.** Until the cutover,
`file_change` is the current table, and the new code writes `kind` on every
insert: without the column the backend does not start.

```sql
ALTER TABLE file_change ADD COLUMN IF NOT EXISTS kind smallint;
```

Nullable and without a default on purpose: it is a metadata-only operation
(it does not rewrite a single row), the old code keeps inserting rows, and
the values of the rows that are already there are computed by the copy from
their `label`.

**1.3.2 Index for the delta passes.** The delta passes filter by
`updated_at`. Without an index on that column every pass scans the whole
heap; with it, it is an index range that only touches the rows that changed.

```sql
-- CONCURRENTLY: it does not block the writes. It cannot run inside a
-- transaction: run it alone.
CREATE INDEX CONCURRENTLY IF NOT EXISTS file_change__updated_at__idx
  ON file_change (updated_at);
```

- If it is interrupted, the index is left `INVALID` and has to be dropped
  and built again:

```sql
SELECT i.indisvalid
  FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
 WHERE c.relname = 'file_change__updated_at__idx';
```

- The index goes with the old table: at the cutover it is renamed to
  `file_change__updated_at__idx_legacy` and disappears with it. The new
  table does not carry it (nothing queries by `updated_at`; the GC uses
  `deleted_at`).

### 1.4 Consumer generalization: audit_log and jobs

**Session settings:** `SET statement_timeout = 0; SET lock_timeout = '5s';`
Re-issue them in each SQL session.

**Step 1 — Stop the legacy archiver and its GC**

1. Before any 2.20.0 worker starts, set `disable-audit-log-archive` and
   `disable-audit-log-gc` in `PENPOT_FLAGS` on all workers. Remove any existing
   `enable-audit-log-gc`; do not leave both tokens. Removing `enable` alone
   does not stop the new GC. There is no
   `:audit-log` flag in the new version: writing full rows follows the
   consumer flags.
2. If the deployment uses the admin console, keep `:admin-console` on
   **on every instance**, web and worker. Each process decides at startup
   whether to write full rows; enabling the flag only on workers does not
   make web instances write them.
   The `:telemetry` consumer (id `0`) ships the anonymized copies
   with the pace of the old cron (10 000 rows, a pass every 3 hours) and its
   first pass replays the shadows the buffer holds. While the old version
   still runs its cron, a copy can reach the endpoint twice; telemetry is
   at-least-once.
3. Roll the workers with these flags. Check each worker's startup log to
   confirm `audit-log-gc` is not active, and wait for active archive and GC
   tasks to finish. Keep `disable-audit-log-gc` in place until phase 5.6.

**Step 2 — Delete what the archiver already archived**

```sql
DELETE FROM audit_log

               WHERE archived_at IS NOT NULL
```

**Step 3 — Pre-apply the jobs step**

```sql
BEGIN;
CREATE TABLE job (
    id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    name         text NOT NULL,
    tenant       text NOT NULL,
    queue        text NOT NULL,
    label        text,

    scheduled_at timestamptz NOT NULL DEFAULT now(),
    retry_num    int NOT NULL DEFAULT 0,
    max_retries  int NOT NULL DEFAULT 3,
    status       text NOT NULL DEFAULT 'new'
                 CHECK (status IN ('new', 'scheduled', 'running', 'retry',
                                   'completed', 'failed', 'cancelled',
                                   'aborted')),
    created_at   timestamptz NOT NULL DEFAULT now(),
    modified_at  timestamptz NOT NULL DEFAULT now(),
    started_at   timestamptz,
    completed_at timestamptz,
    params       jsonb NOT NULL DEFAULT '{}',

    profile_id   uuid NULL REFERENCES profile(id) ON DELETE NO ACTION DEFERRABLE,
    error        jsonb,
    result       jsonb,
    resource_id  uuid NULL REFERENCES storage_object(id) ON DELETE SET NULL DEFERRABLE,
    expires_at   timestamptz
);

CREATE INDEX job__dispatcher__idx
    ON job (tenant, priority DESC, scheduled_at)
    WHERE status IN ('new', 'retry');

CREATE INDEX job__orphan__idx
    ON job (tenant, modified_at)
    WHERE status = 'running';

CREATE INDEX job__profile__idx
    ON job (profile_id, created_at DESC)
    WHERE profile_id IS NOT NULL;

CREATE INDEX job__resource__idx
    ON job (resource_id)
    WHERE resource_id IS NOT NULL;

-- Created in step 8 with the `modified_at` definition.

CREATE INDEX job__expires__idx
    ON job (expires_at)
    WHERE expires_at IS NOT NULL;

CREATE INDEX job__retention__idx
    ON job (modified_at)
    WHERE status IN ('completed', 'failed', 'cancelled', 'aborted')
      AND profile_id IS NULL;

CREATE TABLE job_event (
    id         bigserial PRIMARY KEY,
    job_id     uuid NOT NULL REFERENCES job(id) ON DELETE CASCADE DEFERRABLE,
    kind       text NOT NULL
               CHECK (kind IN ('start', 'progress', 'retry', 'end')),
    payload    jsonb NOT NULL DEFAULT '{}',
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX job_event__job_kind_created_idx
    ON job_event (job_id, kind, created_at DESC, id DESC);

CREATE OR REPLACE TRIGGER deletion_protection__tgr
BEFORE DELETE ON job FOR EACH STATEMENT
  WHEN ((current_setting('rules.deletion_protection', true) IN ('on', '')) OR
        (current_setting('rules.deletion_protection', true) IS NULL))
  EXECUTE PROCEDURE raise_deletion_protection();
COMMIT;
```

If the transaction fails, rerun the whole block.

**Step 4 — Audit log: columns, reserved range and defaults**


**Step 4 — Foreign key, online**

```sql
BEGIN;
SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '10min';   -- measure first; see below
ALTER TABLE file_data
  ADD CONSTRAINT file_data_storage_object_id_fkey
  FOREIGN KEY (storage_object_id) REFERENCES storage_object(id)
  ON DELETE NO ACTION DEFERRABLE INITIALLY IMMEDIATE;
COMMIT;
```

The column is NULL until the backfill, but PostgreSQL still scans the table
(or the index built in the previous steps) to prove there are no violations.
The `SHARE ROW EXCLUSIVE` lock blocks writes for the whole scan, not only
while the lock is acquired: `lock_timeout` bounds the wait for the lock and
`statement_timeout` bounds the scan. A timeout aborts the `ALTER`, releases
the writes and lets you retry in a quieter window; measure the scan in
staging and set the budget accordingly. Retry on `lock timeout`.

Creating it here, before the backfill, keeps the full validation scan out
of the stopped window: the backfill validates each row it writes.

`INITIALLY IMMEDIATE` is required. The storage GC catches the violation
inside the chunk transaction and retries the chunk; an `INITIALLY DEFERRED`
check fires at commit, outside that transaction, and the GC would never
move past a blocked chunk.

## Phase 2 — The deploy to 2.20.0

### 2.1 Full stop and backfill

The backfill runs on every instance, even when no row needs it: an instance
with nothing to backfill updates 0 rows. There is no rolling deploy: the
previous code writes the pointer only to `metadata.storage-ref-id` and its
storage GC reads the reference from there. Running the backfill while that
code serves traffic would leave the rows it writes without a pointer and
could make the GC delete an object a live row still references.

There is no schema rollback after the deploy: the column is the only
reference for the rows 2.20 writes, so a failed upgrade is recovered from the
backup.

**1. Stop every instance (backend and workers).** Keep
`:tiered-file-data-storage` off until every instance runs 2.20.0.

**2. Run the backfill:**

```sql
WITH candidates AS MATERIALIZED (
  SELECT fd.file_id,
         fd.id,
         CASE WHEN (fd.metadata->>'storage-ref-id') ~*
                   '^[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}$'
              THEN (fd.metadata->>'storage-ref-id')::uuid END AS soid
    FROM file_data AS fd
    JOIN storage_object AS so
      ON so.id = CASE WHEN (fd.metadata->>'storage-ref-id') ~*
                          '^[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}$'
                     THEN (fd.metadata->>'storage-ref-id')::uuid END
   WHERE fd.backend = 'storage'
     AND fd.storage_object_id IS NULL
     AND jsonb_exists(fd.metadata, 'storage-ref-id')
     AND (fd.metadata->>'storage-ref-id') ~*
         '^[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}$'
   ORDER BY fd.file_id, fd.id
   LIMIT 5000
 ),
 updated AS (
  UPDATE file_data AS fd
     SET storage_object_id = c.soid,
         metadata = fd.metadata - 'storage-ref-id'
    FROM candidates AS c
   WHERE fd.file_id = c.file_id
     AND fd.id = c.id
  RETURNING 1
)
SELECT count(*) AS rows_updated FROM updated;
```

Run the statement repeatedly, committing each batch separately, until
`rows_updated` is 0. Each batch updates at most 5,000 rows, sets the column and
removes `metadata.storage-ref-id` atomically. The index built in phase 1.5

`storage_object` excludes orphan pointers, and the foreign key validates each

### 3.2 Bulk copy

Copies every row, including the soft deleted ones: the GC manages them the
same way in the new table. `kind` is computed from `label`: a row with a
label is a snapshot, a row without one is a revision.

The pointer of the copy lives in the database, not in the terminal: a batch
can be interrupted and resumed without losing anything.

```sql
CREATE TABLE IF NOT EXISTS file_change_copy_state (
  name    text PRIMARY KEY,
  last_id uuid,
  last_at timestamptz
);

-- for a procedure that already created the table without the mark
ALTER TABLE file_change_copy_state
  ADD COLUMN IF NOT EXISTS last_at timestamptz;

INSERT INTO file_change_copy_state (name, last_id)
VALUES ('bulk', '00000000-0000-0000-0000-000000000000')
ON CONFLICT (name) DO NOTHING;

-- The mark of the delta passes starts at the bulk: the first pass of phase
-- 3.3 covers the rows changed since here, and `DO NOTHING` keeps a re-run
-- from resetting a mark that the passes already moved.
INSERT INTO file_change_copy_state (name, last_at) VALUES ('delta', now())
ON CONFLICT (name) DO NOTHING;

-- The mark is mandatory: a pass without it copies nothing, in silence. The
-- `DROP ... IF EXISTS` keeps this block re-runnable.
ALTER TABLE file_change_copy_state
  ADD CONSTRAINT file_change_copy_state_delta_mark
  CHECK (name <> 'delta' OR last_at IS NOT NULL);
```

Run the create-table block of phase 3.1 first, then this block, then the batch block in a loop until it returns `0`.

One batch (idempotent). It **always returns one row**: the number of rows
it copied, `0` when there is nothing left to copy.

```sql
WITH batch AS MATERIALIZED (
  SELECT id FROM file_change
   WHERE id > (SELECT last_id FROM file_change_copy_state WHERE name = 'bulk')
   ORDER BY id
   LIMIT 10000
),
copied AS (
  INSERT INTO file_change_new (id, file_id, created_at, session_id, revn, data, changes,
                               profile_id, features, label, version, created_by,
                               updated_at, deleted_at, migrations, locked_by, kind)
  SELECT id, file_id, created_at, session_id, revn, data, changes,
         profile_id, features, label, version, created_by,
         updated_at, deleted_at, migrations, locked_by,
         CASE WHEN label IS NOT NULL THEN 1 ELSE 2 END
    FROM file_change
   WHERE id IN (SELECT id FROM batch)
  ON CONFLICT (file_id, id) DO UPDATE
     SET created_at = EXCLUDED.created_at,
         session_id = EXCLUDED.session_id,
         revn       = EXCLUDED.revn,
         data       = EXCLUDED.data,
         changes    = EXCLUDED.changes,
         profile_id = EXCLUDED.profile_id,
         features   = EXCLUDED.features,
         label      = EXCLUDED.label,
         version    = EXCLUDED.version,
         created_by = EXCLUDED.created_by,
         updated_at = EXCLUDED.updated_at,
         deleted_at = EXCLUDED.deleted_at,
         migrations = EXCLUDED.migrations,
         locked_by  = EXCLUDED.locked_by,
         kind       = EXCLUDED.kind
   WHERE file_change_new.updated_at IS DISTINCT FROM EXCLUDED.updated_at
  RETURNING 1
),
-- `moved` advances the pointer only when the batch copied something.
-- PostgreSQL executes a data-modifying CTE exactly once even when the
-- final query does not read its output.
moved AS (
  UPDATE file_change_copy_state
     SET last_id = (SELECT id FROM batch ORDER BY id DESC LIMIT 1)
   WHERE name = 'bulk'
     AND EXISTS (SELECT 1 FROM copied)
  RETURNING 1
)
SELECT count(*) AS copied FROM copied;
```

Repeat this statement until it returns `0`. The `0` comes from the final
`SELECT`, not from a missing row: a batch that finds nothing to copy still
returns it, so it is the signal to stop.

- The pointer is a `uuid` (random order): the pagination is stable but it
  does not group by physical position. The total read is the heap, in a
  scattered order.
- **Estimated duration**: time the first batches and extrapolate. The bulk
  reads the heap plus the live TOAST once (phase 1) and writes about the
  live data. Batches are rows divided by batch size.
- Pace the batches yourself (a pause between statements) if the streaming
  replica falls behind or the backend sees latency. Every batch detoastes
  its share of the TOAST: the cost is I/O, not CPU.
- Watch: replica lag, `pg_stat_activity` (locks between the bulk and
  autovacuum), the space of `pg_wal` and of the data dir.

When the bulk is done, check that no row is missing (it is the check that
matters, not the total count):

```sql
SELECT count(*) AS missing
  FROM file_change o
 WHERE NOT EXISTS (SELECT 1 FROM file_change_new n
                    WHERE n.file_id = o.file_id
                      AND n.id = o.id);
```

`missing` is zero when no row of the old table is absent from the new one;
it is the check that matters. The new table can have **more** rows than the
old one: the GC may have hard deleted a row from the source after the bulk
copied it, and it cleans that row up after the cutover. Rows written during
the bulk are missing until the delta passes pick them up.


### 3.3 Delta passes

Every pass copies the rows modified since the **previous pass**. The
watermark lives in `file_change_copy_state.last_at` (the start of the last
pass; the setup block of phase 3.2 seeds it with the moment of the bulk, so
the first pass covers what changed since then), and the SQL subtracts one
hour of margin, which absorbs the clock drift between the application
(which writes `updated_at`) and the database (which writes `now()`) and the
drift between batches. A row that a pass already copied but did not change
again is not rewritten: the `WHERE` of the `ON CONFLICT` skips it.

```sql
BEGIN;

WITH mark AS (
  SELECT last_at - INTERVAL '1 hour' AS since
    FROM file_change_copy_state
   WHERE name = 'delta'
)
INSERT INTO file_change_new (id, file_id, created_at, session_id, revn, data, changes,
                             profile_id, features, label, version, created_by,
                             updated_at, deleted_at, migrations, locked_by, kind)
SELECT id, file_id, created_at, session_id, revn, data, changes,
       profile_id, features, label, version, created_by,
       updated_at, deleted_at, migrations, locked_by,
       CASE WHEN label IS NOT NULL THEN 1 ELSE 2 END
  FROM file_change, mark
 WHERE updated_at > mark.since
ON CONFLICT (file_id, id) DO UPDATE
   SET created_at = EXCLUDED.created_at,
       session_id = EXCLUDED.session_id,
       revn       = EXCLUDED.revn,
       data       = EXCLUDED.data,
       changes    = EXCLUDED.changes,
       profile_id = EXCLUDED.profile_id,
       features   = EXCLUDED.features,
       label      = EXCLUDED.label,
       version    = EXCLUDED.version,
       created_by = EXCLUDED.created_by,
       updated_at = EXCLUDED.updated_at,
       deleted_at = EXCLUDED.deleted_at,
       migrations = EXCLUDED.migrations,
       locked_by  = EXCLUDED.locked_by,
       kind       = EXCLUDED.kind
 WHERE file_change_new.updated_at IS DISTINCT FROM EXCLUDED.updated_at;

-- The mark is the start of this transaction (`now()`): the rows changed
-- after it are the window of the next pass. Both statements go in the
-- same transaction on purpose; a mark written later would leave a gap.
UPDATE file_change_copy_state SET last_at = now() WHERE name = 'delta';

COMMIT;
```

- Repeat the transaction every 1-6 h (depending on the activity) until the
  pass copies very few rows. With the `updated_at` index of phase 1.3 the
  pass is an index range over the window, so it takes seconds on a quiet
  instance; without it, it scans the heap. To see how many rows are left
  in the window:

```sql
SELECT count(*) FROM file_change
 WHERE updated_at > (SELECT last_at FROM file_change_copy_state WHERE name = 'delta');
```

- The objects GC can keep running. Its soft deletes are covered by the
  watermark, and its hard deletes leave a row with `deleted_at` in the new
  table that the GC itself cleans up later. The hard delete of a **file**
  is blocked while the old table (or the new one) has rows for it, because
  the foreign key on `file_id` is `NO ACTION`. The GC deletes the pending
  files in chunks of 100, and one blocked file aborts the transaction of
  the whole chunk: the chunk is logged as `error on chunk deletion` and
  skipped, its files wait in the trash, and the next daily run retries the
  same chunk and fails again until the cutover. The other chunks keep
  making progress. **Do not run the cutover at the same time as a big
  batch of the GC.**

## Phase 4 — The maintenance window (after the deploy)

### 4.1 Before the lock (online, still 2.20.0 serving)

- One last delta pass (the block of phase 3.3).
- Build the secondary indexes of the new table. The bulk and the delta
  passes only need the primary key (`ON CONFLICT (file_id, id)`), so
  building them here keeps five indexes and their WAL out of every batch.
  The `deleted_at` index carries `file_id` (the primary key is
  `(file_id, id)`): the objects GC needs the `file_id` to lock by pair, and
  with the index it reads the rows it has to delete without touching the
  table.

```sql
-- Secondary indexes: the canonical names, with the _new suffix. There is no
-- index for the system snapshots: the old one filtered them by
-- `data IS NOT NULL`, and with the payload living in `file_data` the column
-- no longer tells snapshots apart. The new one could only filter them by
-- `deleted_at IS NULL`, and the system snapshots always carry a deletion
-- date in the future, so it would never match a row.
CREATE INDEX file_change_new__deleted_at__idx
  ON file_change_new (deleted_at, file_id, id) WHERE deleted_at IS NOT NULL;
CREATE INDEX file_change_new__file_id__revn__idx
  ON file_change_new (file_id, revn);
CREATE INDEX file_change_new__locked_by__idx
  ON file_change_new (locked_by) WHERE locked_by IS NOT NULL;
CREATE INDEX file_change_new__profile_id__idx
  ON file_change_new (profile_id) WHERE profile_id IS NOT NULL;
CREATE INDEX file_change_new__user_snapshots__idx
  ON file_change_new (file_id)
 WHERE label IS NOT NULL AND created_by = 'user' AND deleted_at IS NULL;
```

- Prepare and rehearse the cutover block in staging.
- Pick a low activity window: a freeze of the writes to `file_change` of a
  couple of minutes (the final delta inside the lock copies only the rows
  changed since the last delta pass, so it is quick; the saves of files
  during the freeze fail and the user retries, and the rest of the
  database keeps working). The window has to cover the whole cutover, with
  the backend and the workers stopped and started again (see 4.2).

### 4.2 The cutover (one transaction, a brief exclusive lock)

- **Stop the backend and the workers before the transaction, and start
  them again after it.** The pool keeps server-side prepared statements,
  and a prepared statement holds the OID of the table it was prepared
  with: renaming the table does not change that OID. A connection that had
  already run `insert into file_change` five times (the default threshold
  of the driver) would keep writing to `file_change_legacy` after the
  cutover, and the pool recycles its connections every 30 minutes, so the
  window of silent writes is long.
- Run the transaction, the `ANALYZE`, and the statement that records the
  instant of the cutover (all of it in the block below).
- Start the backend and the workers again.

```sql
BEGIN;

LOCK TABLE file_change IN ACCESS EXCLUSIVE MODE;

-- The final delta: the rows modified since the last pass (its mark, minus
-- the hour of margin). The mark is the one the last pass left.
WITH mark AS (
  SELECT last_at - INTERVAL '1 hour' AS since
    FROM file_change_copy_state
   WHERE name = 'delta'
)
INSERT INTO file_change_new (id, file_id, created_at, session_id, revn, data, changes,
                             profile_id, features, label, version, created_by,
                             updated_at, deleted_at, migrations, locked_by, kind)
SELECT id, file_id, created_at, session_id, revn, data, changes,
       profile_id, features, label, version, created_by,
       updated_at, deleted_at, migrations, locked_by,
       CASE WHEN label IS NOT NULL THEN 1 ELSE 2 END
  FROM file_change, mark
 WHERE updated_at > mark.since
ON CONFLICT (file_id, id) DO UPDATE
   SET created_at = EXCLUDED.created_at,
       session_id = EXCLUDED.session_id,
       revn       = EXCLUDED.revn,
       data       = EXCLUDED.data,
       changes    = EXCLUDED.changes,
       profile_id = EXCLUDED.profile_id,
       features   = EXCLUDED.features,
       label      = EXCLUDED.label,
       version    = EXCLUDED.version,
       created_by = EXCLUDED.created_by,
       updated_at = EXCLUDED.updated_at,
       deleted_at = EXCLUDED.deleted_at,
       migrations = EXCLUDED.migrations,
       locked_by  = EXCLUDED.locked_by,
       kind       = EXCLUDED.kind
 WHERE file_change_new.updated_at IS DISTINCT FROM EXCLUDED.updated_at;

-- Check inside the lock, and abort if it fails: no row of the old table
-- may be missing in the new one. The new table can carry extra rows that
-- the GC hard deleted from the source; it cleans them up after the
-- cutover.
DO $$
DECLARE missing bigint;
BEGIN
  SELECT count(*) INTO missing
    FROM file_change o
   WHERE NOT EXISTS (SELECT 1 FROM file_change_new n
                      WHERE n.file_id = o.file_id
                        AND n.id = o.id);

  IF missing > 0 THEN
    RAISE EXCEPTION 'file_change: % rows of the old table are missing in file_change_new; cutover aborted', missing;
  END IF;
END $$;

-- The old table frees the canonical names (the same names the migration
-- 0158 uses, with the _legacy suffix)
ALTER TABLE file_change RENAME CONSTRAINT file_change_pkey
  TO file_change_pkey_legacy;
ALTER TABLE file_change RENAME CONSTRAINT file_change_file_id_fkey
  TO file_change_file_id_fkey_legacy;
ALTER TABLE file_change RENAME CONSTRAINT file_change_locked_by_fkey
  TO file_change_locked_by_fkey_legacy;
ALTER TABLE file_change RENAME CONSTRAINT file_change_profile_id_fkey
  TO file_change_profile_id_fkey_legacy;

ALTER INDEX file_change__data_ref_id__idx
  RENAME TO file_change__data_ref_id__idx_legacy;
ALTER INDEX file_change__deleted_at__idx
  RENAME TO file_change__deleted_at__idx_legacy;
ALTER INDEX file_change__file_id__revn__idx
  RENAME TO file_change__file_id__revn__idx_legacy;
ALTER INDEX file_change__locked_by__idx
  RENAME TO file_change__locked_by__idx_legacy;
ALTER INDEX file_change__profile_id__idx
  RENAME TO file_change__profile_id__idx_legacy;
ALTER INDEX file_change__system_snapshots__idx
  RENAME TO file_change__system_snapshots__idx_legacy;
ALTER INDEX IF EXISTS file_change__user_snapshots__idx
  RENAME TO file_change__user_snapshots__idx_legacy;
ALTER INDEX IF EXISTS file_change__updated_at__idx
  RENAME TO file_change__updated_at__idx_legacy;

-- And the new table takes them. Only the primary key needs the rename: the
-- `CHECK` and the foreign keys already carry the canonical name (they have
-- no index, so they could take it from the start), and the partitions
-- inherited it.
ALTER TABLE file_change_new RENAME CONSTRAINT file_change_new_pkey
  TO file_change_pkey;

ALTER INDEX file_change_new__deleted_at__idx
  RENAME TO file_change__deleted_at__idx;
ALTER INDEX file_change_new__file_id__revn__idx
  RENAME TO file_change__file_id__revn__idx;
ALTER INDEX file_change_new__locked_by__idx
  RENAME TO file_change__locked_by__idx;
ALTER INDEX file_change_new__profile_id__idx
  RENAME TO file_change__profile_id__idx;
ALTER INDEX file_change_new__user_snapshots__idx
  RENAME TO file_change__user_snapshots__idx;

-- And the tables are swapped. The partitions and their indexes keep the
-- names they were born with (they are named after the partition, not after
-- the table), so there is nothing else to rename.
ALTER TABLE file_change     RENAME TO file_change_legacy;
ALTER TABLE file_change_new RENAME TO file_change;

-- The foreign key of the legacy table goes away: it is `NO ACTION`, so
-- while the legacy table has rows for a file, the objects GC cannot delete
-- that file (it deletes the rows of the file first, and the legacy ones are
-- not its business). The legacy table is frozen: nothing writes to it again.
ALTER TABLE file_change_legacy
  DROP CONSTRAINT file_change_file_id_fkey_legacy;

COMMIT;

ANALYZE file_change;

-- The instant of the cutover, for the checks of phase 5. It goes after
-- the `COMMIT`: inside the transaction `now()` is the start of it (the
-- moment of the `LOCK`), and the rows the final delta copies could pass
-- for writes happened after the cutover.
INSERT INTO file_change_copy_state (name, last_at) VALUES ('cutover', now())
ON CONFLICT (name) DO UPDATE SET last_at = excluded.last_at;
```

- `file_change_legacy` keeps its data and its indexes (with the `_legacy`
  suffix): a frozen copy of the previous layout. Its foreign key on
  `file_id` is dropped, so the objects GC can delete the files again.
- The writes to `file_change` during the lock fail: they are
  seconds-minutes, the affected saves are retried.
- The objects GC and the four RPC commands keep working: same table name
  and same index names after the rename.
- Once the backend is up again, check that the saves go to the partitioned
  table and that nothing went to the table that is going away:

```sql
-- the rows written after the cutover: this one grows with every save
SELECT count(*) FROM file_change
 WHERE updated_at > (SELECT last_at FROM file_change_copy_state
                      WHERE name = 'cutover');

-- the rows that went to the legacy table: this one has to stay at 0
SELECT count(*) FROM file_change_legacy
 WHERE updated_at > (SELECT last_at FROM file_change_copy_state
                      WHERE name = 'cutover');
```

A number above zero in the second query means that some connection was
still writing with a prepared statement of the old table: those rows are
lost when the legacy table is dropped, so they have to be copied over
before that.

### 4.3 The storage backfill is not part of this window

The backfill always runs in the phase 2 stop, before the new instances start.
After the deploy, any row that still carries the pointer is unreadable by
the new code, so this is not a step to defer to the phase 4 window.

## Phase 5 — After the cutover (online)

### 5.1 Partition pruning and access paths

Check that the access paths prune to one partition (when the planner
chooses an index scan):

```sql
EXPLAIN SELECT * FROM file_change
 WHERE file_id = '00000000-0000-0000-0000-000000000000'
   AND id     = '00000000-0000-0000-0000-000000000000';
```

It has to show a single partition (`file_change_NN`), not an `Append` of
16.

### 5.2 Schema parity with the migration, and ownership

Every row of this query has to show `got = expected`:

```sql
SELECT 'columns' AS what, count(*) AS got, 17 AS expected
  FROM pg_attribute
 WHERE attrelid = 'file_change'::regclass AND attnum > 0 AND NOT attisdropped
UNION ALL
SELECT 'partitions', count(*), 16
  FROM pg_partition_tree('file_change') t WHERE t.isleaf
UNION ALL
SELECT 'primary key', count(*), 1
  FROM pg_constraint
 WHERE conrelid = 'file_change'::regclass AND contype = 'p'
UNION ALL
SELECT 'foreign keys', count(*), 3
  FROM pg_constraint
 WHERE conrelid = 'file_change'::regclass AND contype = 'f'
UNION ALL
SELECT 'check constraints', count(*), 1
  FROM pg_constraint
 WHERE conrelid = 'file_change'::regclass AND contype = 'c'
UNION ALL
SELECT 'indexes', count(*), 6
  FROM pg_indexes
 WHERE tablename = 'file_change' AND schemaname = current_schema()
UNION ALL
SELECT 'partitions out of name', count(*), 0
  FROM pg_class
 WHERE relkind = 'r' AND relname ~ '^file_change_new[0-9]'
UNION ALL
SELECT 'child indexes out of name', count(*), 0
  FROM pg_class c
  JOIN pg_index i ON i.indexrelid = c.oid
  JOIN pg_class p ON p.oid = i.indrelid
 WHERE p.relname ~ '^file_change_[0-9]{2}$'
   AND c.relname NOT LIKE p.relname || '_%'
UNION ALL
SELECT 'partition constraints out of name', count(*), 0
  FROM pg_constraint c
  JOIN pg_class t ON t.oid = c.conrelid
 WHERE t.relname ~ '^file_change_[0-9]{2}$'
   AND c.contype <> 'n'
   AND c.conname LIKE 'file_change_new%';
```

The `NOT NULL` constraints are excluded from the last check (`contype <>
'n'`): their names are not stable across server versions, so they are not
part of the parity. The `CHECK`, the primary key and the foreign keys are.

And the names, to compare them with the migration:

```sql
SELECT a.attname AS column
  FROM pg_attribute a
 WHERE a.attrelid = 'file_change'::regclass AND a.attnum > 0
   AND NOT a.attisdropped
 ORDER BY a.attnum;

SELECT indexname FROM pg_indexes
 WHERE tablename = 'file_change' AND schemaname = current_schema()
 ORDER BY indexname;

-- the partitions, with their name
SELECT c.relname AS partition
  FROM pg_class c
  JOIN pg_partition_tree('file_change') t ON t.relid = c.oid
 WHERE t.isleaf
 ORDER BY c.relname;

-- the indexes of the partitions: their name starts with the partition
SELECT c.relname AS child_index
  FROM pg_class c
  JOIN pg_index i ON i.indexrelid = c.oid
  JOIN pg_class p ON p.oid = i.indrelid
 WHERE p.relname ~ '^file_change_[0-9]{2}$'
 ORDER BY c.relname;

-- every table, partition and index of the family shares the owner of the
-- table
SELECT count(*) AS out_of_owner
  FROM pg_class c
 WHERE c.relname LIKE 'file_change%'
   AND c.relkind IN ('r', 'p', 'i')
   AND pg_get_userbyid(c.relowner) <>
       (SELECT tableowner FROM pg_tables
         WHERE schemaname = current_schema() AND tablename = 'file_change');
```

The owner check has to return `0`. If it does not, fix the ownership
before opening the service (re-own the table, the 16 partitions and
their indexes) and re-apply any grants the old table had.

### 5.3 Partition-wise join and autovacuum

- The partition-wise join is already on: the pool of the backend sets
  `enable_partitionwise_join = on` on every connection (it is in the code,
  there is nothing to change in the database role).
- Autovacuum: each of the 16 partitions has its own TOAST (check their
  sizes with `pg_total_relation_size` per partition); with
  `autovacuum_vacuum_scale_factor = 0.2` the threshold is reached earlier
  and in steps. Nothing to change, just watch `last_autovacuum` of the
  partitions the first week.
- The aggregations that do not filter by `file_id` (the team snapshot
  quota and the telemetry counts) read all 16 partitions. To know their
  cost on your instance, time them before and after with
  `EXPLAIN (ANALYZE, BUFFERS)` and compare. The team quota is already
  fixed in the code: it resolves the `file_id` of the team first, which
  lets the planner prune the partitions when it chooses an index scan
  (with a sequential scan it reads all of them).

### 5.4 Drop the helper table and, days later, the old table

```sql
                                 -- dropping the pages, let it roll
```

### 5.6 After every instance runs 2.20.0: turn on the new GC

Once every instance runs this version and the new consumers have replayed
the unarchived buffer, remove `disable-audit-log-gc` and roll the workers to
restore the default GC schedule. The GC deletes the rows the consumers have
passed and applies the 7-day retention of the telemetry shadows. The GC has
two cursor paths: the full rows up to the oldest cursor of the consumers
that read them, and the shadows up to the cursor `0`; a slow telemetry pass
does not retain the full rows. Remove the old archiver flag setting; the new
version does not use it.

The seven-day window limits local retention, not sending. The telemetry
consumer can send older shadows if it reads them before the GC deletes them.

If a consumer registers while a cursor-based GC batch is in progress, it
can miss up to one batch per concurrent GC run that already read the previous
cursor limit. The GC reads the cursors again for each batch but does not lock
out registration. The 7-day shadow retention deletes
independently of cursors. For a complete replay of the buffer, set
`disable-audit-log-gc` on all workers sharing the database and remove any
`enable-audit-log-gc` token. Restart the workers, verify the effective flag
in each startup log, and wait for all queued or running GC jobs to finish
before enabling the new consumer. Do not invoke the
GC manually during the pause. Confirm the consumer has registered and
replayed the buffer before removing `disable-audit-log-gc` and rolling the
workers again. This cannot recover rows the GC already deleted.

To retire the telemetry consumer, turn `:telemetry` off on every instance,
let the GC run once with its cursor frozen and then delete the cursor
(`DELETE FROM audit_log_consumer_cursor WHERE consumer = 0;`). The statement
deletes no shadow by itself: the copies the consumer had not read wait for the
retention window. Turning the flag back on registers the cursor at `(0, 0)`
again and replays whatever the buffer still holds.

## Rollback

- **Before the phase 2 deploy**: phase 1 may have applied out-of-band schema
  changes, but the new code has not started. Keep 2.19 serving; assess and
  reverse the completed phase 1 changes before removing the pre-registration
  rows or switching to the automatic migration path.
- **Partition cutover**: `file_change_legacy` is a frozen copy of the
  previous layout, kept for days. Rolling back before dropping it means
  pointing the code at the legacy layout, which is not supported by the
  release; treat the `DROP TABLE file_change_legacy` as the point of no
  return and schedule it deliberately.
- **Consumer generalization**: the migration keeps the legacy
  `archived_at` mark and its indexes for one release; the two versions can
  coexist during the rollout. Rolling the binaries back is possible while
  `disable-audit-log-gc` is set and the consumers are idle. Keep that
  setting until you are done, and call it a rollback only within the rollout.

## Risks

| Risk | Mitigation |
|---|---|
| Massive WAL during the bulk copy (proportional to the copy) | Throttle between batches; watch `pg_wal`, the replication slots and the replica lag |
| Latency seen by the application during the bulk | Throttle; low traffic hours; the bulk is I/O and does not block writes |
| `updated_at` not reliable in rows changed before the deploy | The deploy goes before the bulk (phase 2.2); the delta passes cover from the start of the bulk |
| Lock/unlock/soft delete during the passes | Covered by the watermark; the cutover includes the final delta inside the lock |
| Hard delete of the GC between passes | The row is left with `deleted_at` in the new table; the GC cleans it up later |
| Orphan rows if a `file` is deleted halfway | The foreign key on `file_id` is `NO ACTION`: the GC deletes the rows of the file before the file, so a chunk that fails leaves the file in the trash and the next run deletes it |
| The files in the trash cannot be deleted while the legacy table has rows for them | The foreign key of the legacy table is dropped at the cutover; until then the files wait in the trash |
| Saves failing during the lock of the cutover | Freeze of minutes in a low traffic window; manual retries |
| Planner regression after the cutover | Immediate `ANALYZE` + the pruning `EXPLAIN`; the pool already sets the GUC |
| Clock drift between the application and the database | The delta window starts an hour before the bulk; the margin absorbs the drift |
| `CONCURRENTLY` build interrupted, index left `INVALID` | Drop it and rebuild it; `IF NOT EXISTS` matches by name and would accept the broken index: the gates (phase 1.4 step 9 and phase 1.5 verify) are mandatory |
| Running the backfill while 2.19 serves | Do not: phase 2 stops every instance before the backfill |

## Success metrics

- After the cutover: `file_change` (partitioned) holds at most the
  `pg_table_size` of the old table (phase 1).
- After the `DROP` of the old table: the database shrinks by about the
  size that table had.
- The access paths that filter by `file_id` (the lookup of a snapshot,
  the quota of a file and the lock of the GC by pair) prune to one
  partition when the planner chooses an index scan (`EXPLAIN`). The quota
  of the team and the discovery of the GC do not filter by a single file:
  they read all the 16 partitions.
- No visible change for the user.
